## 0. 一句話

使用者把藥錠拿反了、或把 `S` 看成 `5`，目前會得到「找不到」——本次新增**第五分區**接住這批，且**不得**動到現有四區的任何一筆、**也不得**讓該區大到在藥車前不可用。

---

## 1. 目標

1. imprint 查詢在**原樣比對失敗**時，額外嘗試兩種確定性變體：**180° 倒讀**與**字形相近壓平**。
2. 變體命中的記錄進入**獨立的第五分區**，卡片明示觸發理由（倒讀／字形相近／兩者）。
3. 現有四分區的成員**逐筆不變**，僅 `excluded` 減少。
4. **變體區的規模必須被持續監看**——規則漂移由指紋抓（A17），資料漂移由發布守門抓（C21）。
5. 全部在前端純函式層完成：**不動產品資料管線、不動 `appearance.json`、不重跑圖片鏡像**。

## 2. 非目標（本次明確不做）

| # | 不做 | 理由 |
|---|---|---|
| **N15** | **組合變體**——包括「倒讀後再壓平」與**「不同 token 分別靠不同規則拼成一次全中」** | 後者是 v0.1 的漏洞：只寫「變體全中」而未定義全中的單位，等於從後門放進組合變體（Codex 1.1）。§5 的 admission truth table 把它堵死 |

| 表 | 內容 | 帶可倒讀 token 的記錄 | 新 token | 撞既有真實刻字 |

| B 核心＋`3↔E`（16 字元）／C 積極（20 字元） | 未採用 | — | — | — |

**最壞案例（v0.1 曾寫反方向，此處為實跑值）**：
真實刻字 token `SH` = **3 筆**、`HS` = **42 筆**。
查詢 `SH` 時主區 **37 筆**（完全 3／字首 22／包含 12），倒讀成 `HS` 後變體區 **42 筆**——**變體區比主區還大**。
這一格是「變體絕不可混進主區」與「規模必須被持續監看」（A17／C21）的直接證據。

> v0.1 把這組寫成「`HS` 真實只有 3 筆」，是把**記錄端**的展開量測當成**查詢端**語意。
> 這是本 repo 第四次犯「從已聚合產物回推語意」（`plan.md` §3.2 已警告三次）。

### 3.2 字形相近（三組候選實測，選 Q）

| 組 | 類 | 帶可壓平 token 的記錄 | 放大倍率（中位／p90） | 最貴的一組 |

### 3.3 這些數字是**規模上界**，不是驗收數字

§3.1／§3.2 量的是「資料集裡有多少筆帶有可倒讀／可壓平的 token」。
任一具體查詢的變體區筆數**取決於查詢本身**，一律由 oracle（`tools/make-expected.mjs`）對具名查詢獨立產生（C20）。
**本節任何數字都不得出現在驗收條件裡。**

### 3.4 規則收斂的實測依據（S1，本次的第四個 Blocker）

拿全部 **2,357 個真實 token 各自當查詢**實跑，變體區筆數分佈：

| 規則 | 中位 | p90 | p99 | 最大 | >100 筆的查詢 |
|---|---|---|---|---|---|
| v0.1（放行字首級 ＋ 單字元也壓平）| 0 | 2 | 66 | **801**（查 `I`）| 15 個 |
| 單字元不做字形變體 | 0 | 1 | 42 | 234 | 7 個 |
| ＋單字元倒讀只用完全級 | 0 | 1 | 40 | 206 | 4 個 |
| **v0.2 採用：變體一律只接受「完全相等」** | 0 | **1** | **12** | **84** | **0 個** |

查 `I` → 801 筆、`5` → 768 筆、`L` → 643 筆。**這是威脅模型第 2 條「假陽性淹沒真陽性」的教科書案例。**
v0.1 的每一條驗收都在驗「該中的有沒有中」，**沒有一條會抓到這個**——故新增 A17。

### 3.4.1　v0.2 的 A17 查詢母體錯了：真實 token ≠ 合法查詢域（第二輪 Blocker）

v0.2 的 A17 以「2,357 個真實 token 各自當查詢」為母體，得到最大 84 筆。
**但使用者輸入的是任意字串，不是資料裡已有的 token。** Codex 第二輪找到反例、主持人實跑驗證屬實：

`Y5P` **不是**真實 token，`YSP`（永信）**是**，且 `canon('Y5P') === canon('YSP') === 'Y5P'`。
查詢 `Y5P` 時原樣命中 0 筆 → **變體區 111 筆**，而它不在 A17 的母體內。

主持人另掃**完整可達查詢閉包**（3,103 個查詢 = 真實 token ∪ `flip(t)` ∪ 各 canon 類代表字）：

| 指標 | 值 | 出處查詢 |
|---|---|---|
| **閉包最壞變體區** | **111** | `Y5P` |
| `flip` predicate 上界 | **84** | `W`（倒讀 `M`）|
| `canon` predicate 上界 | **111** | canon 類 `Y5P` |
| 真實 token 當查詢的最壞值 | 84 | — |

**這是取樣偏誤**，與 v0.1 在 A15 犯的是同一類錯：拿手邊有的樣本當成完整輸入空間。

### 3.4.2　但 111 是正確答案，不是規則失控

超過 100 的案例**全部是同一個模式**：

| 查詢 | 對應真實刻字 | 筆數 |
|---|---|---|
| `Y5P` | `YSP`（永信）| 111 |
| `5T` | `ST` | 96 |
| `5TD` | `STD` | 81 |
| `5YN` | `SYN` | 64 |

**全部是「把廠商前綴的 `S` 看成 `5`」——這正是本功能要解決的情境。** YSP 本來就印在 111 個產品上。
唯一能壓下它們的規則是「canon 類記錄數超過門檻時整條 predicate 停用」，那會讓**最常見**的誤讀情境反而查不到，等於用漏檢換清單長度，直接違反 D1。

**使用者裁決（2026-08-14）**：111 筆在預設收合、標題顯示筆數的分區裡，藥車前可接受 → **放棄絕對上界**。

絕對上界原本是壓制 801 筆的**設計逼迫工具**；規則收緊後最壞值降到 111，逼迫工具已完成任務。
留作永久 release gate 是錯的工具——調高常數到 111 以上正是 repo 明令禁止的「改常數讓測試變綠」。
**A17 因此改為規則指紋，規模的臨床防護回到既有機制**（預設收合 ＋ 標題筆數 ＋ §8.4 候選過多提示）。

## 5. Admission contract（**唯一語意來源**，其他章節只引用不重述）

> Codex 4.3：v0.1 把同一組邊界散在 D31／D34／N15／N16／A14／B22 六處。
> 那正是本 repo 記過的「規格與實作同一人先後寫會漂移」的溫床。**以下這張表是唯一真理來源。**

### 5.1 何時計算變體

| imprint 原樣狀態 | 計算變體？ | 結果分區 |
|---|---|---|
| `OFF`（輸入 trim 後為空）| **否** | 條件未啟用（D1.1 階段 ①）|
| `NO_TOKEN`（非空但 0 token，如 `無`）| **否** | 不套用 imprint 篩選（D3）|
| `MATCH` | **否** | 主區 tiers 0／1／2 |
| `PARTIAL` | **否** | 部分符合區（D17）|
| `UNKNOWN`（記錄兩欄皆無 token）| **否** | 未提供區（D1）|
| **`MISMATCH`** | **是** | 見 §5.2 |

**「原樣失敗」是逐記錄判定，不是整次查詢**（Codex 1.6）。同一次搜尋中主區與變體區可以同時非空——實測查詢 `SH` 主 37／變 42。

### 5.2 變體判定：兩條**獨立** predicate

兩條規則各自必須**單獨覆蓋全部查詢 token**。**不得**把不同 token 的不同規則命中拼成一次全中（N15）。

| predicate | 前置否決 | 命中條件 |
|---|---|---|
| **倒讀 `flip`** | 任一查詢 token 的 `flip()` 為 `null` → 整條 **false**；全部 token 皆為 fixed point（`flip(q)===q`）→ 整條 **false** | **每個**查詢 token 的 `flip(q)` 都與某個記錄 token **完全相等** |
| **字形 `canon`** | **任一查詢 token 長度為 1** → 整條 **false** | **每個**查詢 token 的 `canon(q)` 都與某個記錄 token 的 `canon(t)` **完全相等** |

- **只接受「完全相等」**——不啟用字首級、不啟用包含級（依據 §3.4）。
- 任一 predicate 為 true → **把 imprint 條件由 `MISMATCH` 置換為 `Cond.VARIANT`**；理由 = 為 true 的那些；兩條皆 true → 雙理由。
- 皆 false → 維持 `Cond.MISMATCH`（照舊排除）。

> **「置換」不是「並存」。** 若實作成兩個狀態同時保留，按 §5.3 的 `mismatch > variant`，記錄仍會被排除——
> **功能會靜默地完全不存在，而所有正例測試看起來都合理。** 其他條件照既有優先序合成，不受此置換影響。

### 5.3 分區優先序

```
mismatch > variant > unknown > partial > main
```

`variant` 排在 `unknown`／`partial` 之前**不是因為它更確定**，而是因為它只可能由「原本會被排除」產生，所以擺在哪裡都不會從既有分區搬走任何一筆；擺前面則保證卡片顯示使用者最需要知道的理由（「你可能看反了」）而不是被「TFDA 沒填顏色」蓋掉。

**由此得到不變量（A13）**：
```
main / partial / unknown 三區的 ordered ID 序列，開啟變體前後逐筆相同
excluded_after + |variant| === excluded_before
```

## 6. 架構決策

### D30　新增第五分區 `variant`「刻字可能看反或字形相近」

**問題**：使用者把藥錠倒著拿（`6` 讀成 `9`），或把 `S` 讀成 `5`、`I` 讀成 `1`。目前一律落入 `Cond.MISMATCH` → 完全排除 → 看到「找不到」。現有四區都接不住：`unknown` 要求欄位沒填、`partial` 要求至少一個 token 原樣命中。

**為什麼不混進主區**：§3.1 的查詢 `SH` 主 37／變 42——混進去等於讓 42 筆猜測與 37 筆事實不可分辨。
**為什麼不用加權評分排到後面**：違反 F8，且分數是不可稽核的旋鈕。

### D31　變體只在 imprint 為 `MISMATCH` 時計算

語意見 §5.1。三點補充：

1. **「原樣已命中的記錄不會重複進變體」是本規則的推論，不另立規則。** 原樣命中的記錄根本不會進入變體計算路徑。**不得**為此另寫一條去重規則——那會產生兩個真理來源（判定 1.3）。
2. **變體區不完整揭露其他 `unknown` 原因，這是刻意接受的取捨**（判定 2.3）。一筆記錄可能同時是 imprint variant 且顏色 unknown；優先序讓它進 variant 區，分區名稱因此只揭露刻字假設。**不新增第六區、不擴充結果模型**；缺值資訊沿用卡片既有的「未提供」欄位標示。
3. 其他條件（顏色／形狀／刻痕／名稱）的 `mismatch` **繼續壓過** `variant`——變體不得被實作成提前返回而繞過 AND（A14 交叉格）。

### D32　倒讀：`flip()` 一對一映射，**只作用於查詢 token**

```
自映射：0 1 8 H I N O S X Z
互映射：6↔9   M↔W
```

**方向明定**（Codex 1.4）：**只轉換每個查詢 token，再與原始記錄 token 比對。**
撤回字首級後兩個方向因對合而等價，**但語意不得靠「碰巧等價」成立**——B22 只負責驗證，不負責定義。

- `flip(tok)` = 反轉字串後逐字查表；**任一字元不在表中即回 `null`**（不得回原字串，否則「無變體」與「變體恰為自身」無法區分）。
- **fixed point 不算變體**：`flip(q) === q` 時該 token 不提供倒讀證據。fixed point **不只是單字元**——實測 `flip('69')==='69'`、`flip('MW')==='MW'`（Codex A15c）。
- 不含 `3↔E`：鏡像只在特定字體成立，`E` 是高頻字母。
- 不含 `L↔7`、`2`／`5` 自映射：`2` 與 `5` 倒讀後更像彼此而非自己，已由 D33 覆蓋，放進倒讀表會兩條規則重複觸發同一筆。

### D33　字形相近：**canonical 壓平**，雙邊對稱，單字元不啟用

5 類各取第一字元為代表：`0 O → 0`、`1 I L → 1`、`5 S → 5`、`2 Z → 2`、`8 B → 8`。
查詢與記錄 token **雙邊都壓平**後比對——**這是對稱的等價關係**：查詢 `0` 能接住記錄 `O`，查詢 `O` 也能接住記錄 `0`（判定 1.3）。

**單字元查詢不啟用字形變體**（S1）：單字元壓平等同「刻字第一個字母看起來像 5」，與 D18 判定不可用的包含級同性質。實測若啟用，查詢 `I` 變體區 801 筆、`5` 768 筆、`L` 643 筆。
**單字元的倒讀保留**——把藥翻過來 `6` 變 `9` 是真實物理情境，實測查 `6` 只多 10 筆、`9` 多 15 筆。

**為什麼壓平不展開**：展開是笛卡兒積，`S15` 會生 12 個查詢；壓平把它變成 O(1)。
**為什麼是 Q 5 類**：R 8 類加入 `D/Q`（`D` 高頻）等，放大倍率與誤放行同步上升；P 2 類漏掉 `5/S`——那正是藥師實際會看錯的那組。

### D34　變體比對**只接受 token 完全相等**

不啟用字首級、不啟用包含級（比 D18 更嚴），且不接受變體的部分符合（N16）。

**依據是 §3.4 的實測**：放行字首級時變體區最壞 801 筆；只接受完全相等時最大 84 筆、p99 12 筆、**無任何查詢超過 100 筆**。

**這是刻意接受的漏檢**，與 D18 同一條取捨線：留著字首級等於用不可用的清單換理論涵蓋率。被排除的情境列入 §10。

### D35　`resultStates()` 的 `ONLY_UNCERTAIN` 必須納入 `variant` 筆數

```js
const uncertain = result.partial.length + result.unknown.length + result.variant.length;
```

**不改會怎樣**：`mainCount === 0` 且只有變體區有值時 UI 會回 `EMPTY` 並顯示「找不到」——**畫面上明明列著候選，文案卻說找不到**。實測查詢 `S15` 正是此情境（主 0／變 1）。

### D36　與 N6／F8 的界線

| fuzzy（N6 禁止） | 本次（D32／D33／D34） |
|---|---|
| 距離門檻可調，改一個數字就改變結果集 | 字元表由規格凍結，改動須走 D13 四處同步 |
| 產生相似度分數並排序 | 無分數、無門檻、無排序（F8 不變）|
| 結果混入主區 | 獨立分區，卡片標示觸發理由 |
| 覆蓋範圍隨資料變動 | 可逐字列舉（14 字元 ＋ 5 類），可由 oracle 獨立重算 |

### D37　變體結果是 **identity 與 reason 不可分割的單一 query-scoped 契約**

v0.2 寫成 `variant[]` ＋ 獨立的 `variantReasons`——**那是兩個必須同步的結構**，
oracle、production、UI 會各自選一種對齊方式（ID 鍵控？陣列位置對齊？），排序後理由就會貼錯卡（Codex 2.2／4.2）。

**v0.3 定為單一契約**：變體區的每個元素同時攜帶記錄身份與理由集合，兩者不可分離。

- 理由由**每次搜尋產生**，**不得寫回** indexed item（`_tok`／`_tokCanon` 所在的物件）。
  `app.js` 有 120 ms debounce（`app.js:18`），快速輸入時連續搜尋是常態——理由若掛回 item，
  **上一個查詢的 stale reason 會顯示在這一個查詢的卡片上**。
- 同一記錄 ID 在變體區**至多一筆**；理由為集合 `{flip}`／`{canon}`／`{flip, canon}`，**不得為空集合**。
- **理由的 domain 與變體區的 ID set 必須完全相等**——不是「每個 variant 都找得到理由」（那允許多餘的 reason entry），是雙向相等。
- 連續兩次不同查詢**不得共享理由狀態**；第二次搜尋**不得改變第一份結果**（可重入，由 E12 具名驗證）。

## 7. 資料流

**無產品 canonical data pipeline 變更**（`build`／`publish`／圖片鏡像／`appearance.json` 全部不動）。
**但允許 CI 對 staging 資料新增唯讀驗證**——C21 需要它，見 §9 的 C 組。

全部發生在瀏覽器載入之後：

```
appearance.json（位元組不變）
  → indexItems()      : 每筆算 _tok（既有）＋ _tokCanon（新增，記憶體，索引階段一次性；實測 12 ms）
  → search(criteria)  : 每筆 evaluate()，依 §5 的 admission truth table
  → 回傳 { tiers, partial, unknown, variant, excludedCount,
           mainCount, imprintQueryState }
                       ↑ variant 的每個元素同時攜帶記錄身份與理由集合（D37 單一契約）
  → resultStates()    : uncertain 納入 variant
  → app.js 渲染第五區（預設收合，排在未提供區之後）
```

**失敗行為**：**無新增 I/O 或網路失敗路徑**；新增的是**語意與結果契約**的失敗（理由漂移、重入污染、規則跨界拼接、UI 狀態漏算），由 A／B／E／F 組驗證（Codex 1.9）。
資料載入仍由 D16 fail-closed 守著；SW 六條不動。

## 8. UI 規格（增補 §8.2）

- 分區順序：完全 → 字首 → 包含 → 部分符合 → 未提供 → **變體（新，最後）**
- 排最後的理由：未提供區至少「這顆藥沒有和你的輸入牴觸」；變體區是「你的輸入和它牴觸，但如果你看反了就不牴觸」——多疊一層假設。
- 標題：「**刻字可能看反或字形相近（N）—— 這些藥的刻字與你的輸入不同，但在轉向或字形相近的情況下可能是同一顆**」
- **預設收合**（沿用 v1.7 的低確定性結果收合）
- 每張卡片標示**該卡自己的**觸發理由：`倒讀`／`字形相近`／兩者
- 不顯示任何分數、百分比、相似度、排名（F8）
- 區內排序沿用 `compareItems`

## 9. 驗收條件

> 每條的 **[堵死]** 段回答：什麼樣的弱化實作會讓這條通過、但功能其實是壞的？
> **v0.2 的 [堵死] 段已經 Codex 逐條反驗過**——v0.1 有多條是「宣稱堵死」而非真的堵死。

### A 組 — 搜尋語意

**A13　既有三區逐筆不變 ＋ excluded 差額恆等 ＋ 變體身份**

對以下 **12 組具名 criteria**（**全部列名，不用「≥12」留替換空間**）：

`T`／`S`／`10`／`M 40`／白+圓形+無+`S`／`無`（零 token）／白+圓形+無（無 imprint）／`SH`／`HS`／`01`／`12`／`S15`

斷言四件事：
1. `tiers[0..2]`、`partial`、`unknown` 的 **ordered ID 序列**與凍結 baseline 逐筆相同
2. `variant` 的 **ordered ID 序列**與 oracle 凍結值逐筆相同
3. **每個 variant ID 的理由集合**與 oracle 凍結值相同
4. `excludedCount + variant.length === excludedCount_baseline`

baseline 來源明定為**已凍結的 expected manifest**，**不得新增產品層功能旗標**（撞 N18）。

**[堵死]** v0.1 只有第 1、4 條 → 一個「從 excluded 任意挑 N 筆塞進 variant」的實作能同時滿足序列不變與恆等式，錯放的藥仍全綠。第 2、3 條驗的是**身份與理由**，不是守恆。

---

**A14　`variant` 只由 imprint `MISMATCH` 產生（八狀態具名矩陣，分兩類）**

對 imprint 的八種狀態各建具名 fixture，**但兩類的要求不同**——v0.2 要求「八格每個都構造成變體 predicate 亦為 true」是**邏輯上不可實現**的（Codex 驗證）：

| 類 | 狀態 | 要求 |
|---|---|---|
| **甲：predicate 可成立** | `MATCH-EXACT`／`MATCH-PREFIX`／`MATCH-CONTAINS`／`PARTIAL` | fixture **必須構造成變體 predicate 亦為 true**（counterfactual），否則移除 MISMATCH guard 時測試不會紅。**這四格才是 F13-1 的守門者** |
| **乙：predicate 不可能成立** | `OFF`／`NO_TOKEN`／`UNKNOWN` | **只驗結果**（不得出現在 variant 區、須落在 §5.1 指定分區）。`OFF`／`NO_TOKEN` 沒有查詢 token 可供 predicate 評估；`UNKNOWN` 定義為記錄無任何 token，不可能與轉換後 token 完全相等。**不得宣稱這三格能殺死 guard mutation** |

> 強求乙類滿足不可滿足條件，只會逼實作者加入不屬於產品語意的測試鉤子，或悄悄弱化 fixture——
> 最後規格與測試各說各話。

**交叉格**：對 `MISMATCH` × 其他條件 `MATCH`／`UNKNOWN`／`MISMATCH` 三種：
- 其他條件 `MISMATCH` → **必須 excluded**（變體不得繞過 AND）
- 其他條件 `UNKNOWN` → 依 §5.3 **必須進 variant，不得進 unknown**

**[堵死]** v0.1 只測 exact MATCH／PARTIAL／UNKNOWN 三格，且把顏色形狀都設成 match——正好避開「變體提前返回繞過 AND」這個風險，是取樣偏誤。

**A17　可達查詢閉包的**規則指紋**（v0.3 改寫）**

**查詢域是完整可達查詢閉包，不是真實 token**：
```
閉包 = 真實 token ∪ { flip(t) : t 為真實 token, flip(t) ≠ null } ∪ { 各 canon 類的代表字 }
```
現行 baseline 為 **3,103 個查詢**（v0.2 的 2,357 是取樣偏誤，漏掉 `Y5P` 這類可達但非真實 token 的輸入）。

對該閉包實跑，斷言**三個凍結指紋逐一相等**（不是上界，是等值）：

| 指紋 | 凍結值 | 出處 |
|---|---|---|
| 閉包最壞變體區 | **111** | `Y5P` |
| `flip` predicate 上界 | **84** | `W` |
| `canon` predicate 上界 | **111** | canon 類 `Y5P` |

**任一數字變動即紅。** 這條守的是**規則漂移**，不是政策門檻——
**不設絕對上界**（依據 §3.4.2 與使用者裁決）。p99 僅作報告指標輸出，**不列為 gate**。

**[堵死]** v0.2 版本有兩個問題，都已修：
- **不足**：母體是真實 token，`Y5P → 111` 這種合法輸入測不到。改用閉包後測得到。
- **過頭**：把描述性統計 p99=12／max=84 升格為永久 release gate，週更後合法資料會誤攔。改為指紋（等值比對，變動時人工裁決）＋ C21（守資料）。

實測驗證這條仍能抓住它該抓的：F13-7（放行字首級）→ 閉包最壞值上升 → 紅；F13-12（單字元啟用字形）→ 查 `I` 得 801 筆 → 紅。

### B 組 — 正規化（純函式，系統性窮舉）

**B20　`flip` 的映射正確性、對合性、表外行為**
1. **逐字斷言完整 14 個映射**（`0→0`、`6→9`、`9→6`、`M→W`、`W→M`…全部列出）
2. 對**其餘全部 22 個 `[A-Z0-9]` 表外字元** × **首／中／尾三個位置**斷言 `flip(s) === null`（保留 `OST` 具名）
3. 對實際 token 中**可 flip 的那些**斷言對合（`flip(t) !== null` ⇒ `flip(flip(t)) === t`）。**表外 token 由第 2 條的 `null` 契約分開驗**——照字面對「全部 2,357 個」斷言對合，對 `flip(t) === null` 者無法成立
4. 至少一個**長度 > 3** 的具名向量
5. 具名向量：`flip('6')==='9'`、`flip('69')==='69'`、`flip('MW')==='MW'`、`flip('SH')==='HS'`、`flip('TA')===null`

**[堵死]** v0.1 只驗長度 1–3 的對合 ＋ ≥20 個表外案例。**對合證明不了映射正確**——把兩個自映射字互換（如 `H↔I`）仍然是對合。第 1 條逐字斷言才堵得住。第 2 條的「首／中／尾」堵住「只檢查首字元」的實作。

**B21　`canon` 的映射正確性、冪等、值域**
1. **逐字驗五個等價類的每個成員**都映到指定代表字（`O→0`、`I→1`、`L→1`、`S→5`、`Z→2`、`B→8`）
2. 對**其餘全部 `[A-Z0-9]` 字元**驗 identity（`canon('D')==='D'`）
3. 對 2,357 個實際 token 全量驗冪等與值域（結果不得含 `O I L S B Z`）
4. 具名向量：`canon('SILO')==='5110'`、`canon('B2')==='82'`、`canon('012')==='012'`

**[堵死]** v0.1 的冪等＋值域＋3 向量仍放行「`Z` 被刪除」或「`Z` 映成 `8`」。第 1、2 條逐字釘死才堵得住。

**B22　變體只接受完全相等，且兩條規則不得拼接（含對照組）**
- **單 token 否定**：記錄 token `HSY`、查詢 `SH`（`flip`→`HS`）→ `HSY` 非完全相等 → **不得**進 variant
- **單 token 對照組**：記錄 token `HS` → **必須**進 variant，理由 `{flip}`
- **多 token 否定 1**：任一 token 只能字首或包含命中 → 整條規則失敗
- **多 token 否定 2（N15 守門，v0.3 補上真實 witness）**：
  查詢 **`W L30`** vs 記錄 **`衛署藥製字第034807號`**（token `M, T, 130, HOPER`）——
  `W` 靠倒讀命中 `M`、`L30` 靠字形命中 `130`，但 `flip('L30')` 因 `L` 表外回 `null`（倒讀整條 false）、
  `W` 為單字元（字形整條 false）→ **兩條規則都不全中，必須排除**。
  逐 token OR 變異下會被誤放行 → 這是 F13-10 的守門者
- **多 token 對照組**：同一規則覆蓋全部 token → 必須進 variant
- **雙理由對照組**：兩條規則**各自獨立**全中 → 進 variant 且理由為 `{flip, canon}`

**[堵死]** v0.1 只有單 token 正反例 → 一個「多 token 時重新允許包含級」或「多 token 時逐 token OR 兩規則」的實作完全通過，而後者正是 N15 的笛卡兒積入口。沒有對照組時，「變體功能整個沒接上」也會讓所有否定斷言全綠。

### C 組 — oracle 獨立性

**C20　`tools/make-expected.mjs` 對變體規則維持獨立雙實作**
1. **靜態斷言（剝除註解後）：禁止 oracle 依賴 production 搜尋語意的<u>整個本地 dependency closure</u>**——
   不只禁 `search.js`。v0.2 把「只禁兩個字串」改成「禁止任何指向 `search.js` 的 import」仍然不夠：
   **把共用語意搬到第三個本地模組讓兩邊一起 import，靜態斷言照樣通過，而獨立性根本不存在。**
   斷言必須遞迴解析 oracle 的 import 圖，確認其中不含任何 production 搜尋語意模組。
   （這與 CLAUDE.md 記的「變異存活先懷疑斷言錨錯位置」是同一條。）
2. oracle 獨立實作 `flip`／`canon`／admission truth table，並輸出**每個具名查詢的 ordered variant IDs ＋ 每個 ID 的理由集合**（不只筆數）
3. 具名查詢**至少涵蓋六類**：M/W（`MS`，變 44 含倒讀 43）／5/S（`10`，字形 15）／表外字元（`TA`）／fixed point（`MW`、`69`）／多 token 不得拼接（`M 40`）／雙理由（`01`）
4. **雙向 mutation 對帳**：對 **oracle** 與 **production** 分別施加同類規則變異（移除 `M↔W`、移除 `5/S`、放行字首級），**兩邊都必須讓 manifest 對帳失敗**
5. 規則有意變更時走 D13 四處同步

**[堵死]** v0.1 的靜態斷言只禁兩個字串，且只要求硬編筆數 → oracle 與 production **各自錯放同樣數量的不同藥**時完全對得上，兩邊全綠。第 2 條的 ordered IDs ＋ 理由集合堵死它。第 4 條堵死「自檢寫了但永遠不 fail」以及「oracle 變異會紅但 production 變異不會」。

---

**C21　發布守門：對<u>待發布資料</u>動態重算閉包（v0.3 新增）**

A17 讀的是凍結 baseline，**因此它只守規則、不守資料**。而週更流程是先 `npm test`（讀 `tests/baseline-2026-08-12.json`）、之後才 publish staging（`.github/workflows/update-data.yml`）——
**TFDA 新增一批高頻刻字時，A17 完全不會知道。** 目標 4 要的正是後者。

- `verify-data` 在發布前對 **staging 的 `appearance.json`** 重算完整可達查詢閉包（實測 **853 ms**，成本可忽略）
- 與**前一版已發布的指紋**比對，**顯著上升時 fail-closed，要求人工裁決**
- **不綁絕對常數**（不重複 A17 的錯誤，也不製造「合法資料被無理由攔下」）
- 這是**唯讀驗證**，不改任何產品資料管線（§7 已相應改寫措辭）

**[堵死]** 若只有 A17，一個「規則沒變、但資料讓變體區膨脹到不可用」的週更會**靜默發布**，而所有測試全綠——
因為測試讀的是三個月前的凍結快照。分成兩層（A17 守規則／C21 守資料）才是 D13 紀律在這條上的正確投影。

### E 組 — UI

**E12　變體區的可見行為（逐卡定位，不掃全頁）**
- 變體區存在、標題含筆數、**預設收合**、排在未提供區之後
- 對**渲染後的 variant section 逐卡定位**，以記錄 ID 對照 oracle 的 expected reason set：
  - 單理由卡**不得**含另一個理由詞
  - 查詢 `01` 的那 1 筆雙理由卡**必須同一張卡**同時含「倒讀」與「字形相近」
- 禁語（`%`、`分數`、`相似度`、`排名`）**只掃 UI 自產生的理由與標題文字**，**不掃資料欄位、不掃原始碼**——
  藥品品名或劑量本來就可能含 `%`（例如 `5%` 葡萄糖），掃全區會誤觸而讓這條變成雜訊
- 查詢 `S15`（主 0／變 1）時**不得**渲染 EMPTY 文案（接 A16、F13-6）
- **可重入性（v0.3 新增，D37 的驗證，F13-11 的守門）**：具名一個**同 ID 在兩次查詢中理由不同**的 witness，連續執行兩次搜尋後斷言三件事：
  1. 第二次搜尋**不改變第一份結果**的理由
  2. 兩份結果**各自**符合 oracle
  3. **indexed item 在搜尋前後都不含任何 query-scoped reason**

**[堵死]** v0.1 掃全區文字 → 把兩個理由詞固定放在**區標題**就能讓雙理由斷言通過，而每張卡的理由可能全錯。
v0.2 加了逐卡定位，但**只驗單次搜尋** → 理由若以可變參照掛在 item 上，單次搜尋與逐卡 UI 都會正確，
直到連續查詢或保存第一份結果後才污染。**F13-11 是第二輪唯一被判定「未成立」的變異**，上面三條斷言堵死它。
