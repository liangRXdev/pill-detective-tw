## 2. 架構風險

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **Blocker** | D1.1 的每列並非互斥。例：`S` 為空且記錄顏色空時，同時符合 `match` 與 `unknown`；刻痕為「不限」且記錄空、Q 為空且 token 集合空亦同。不同實作者可合法得到不同初始結果與未提供區。 | 這會寫進搜尋核心、初始 UI、計數與整套 A 組 expected sets；晚修等於重寫核心語意與大量驗收。 | 先判斷條件是否啟用：**未啟用一律 `match`，不查看記錄缺值**；僅對已啟用條件判定 `match/mismatch/unknown`。把這個優先序直接寫進真值表。 |
| **Blocker** | imprint 存在未涵蓋組合：輸入非空，但正規化後零 token，例如「無」、純中文或只有符號。依目前「每個 Q token 皆命中」，空集合會真空成立而使所有有 token 記錄 match；若把零 token 視為 Q 空，又會把所有記錄視為 match。兩者都與 A8「搜尋無不命中任何記錄」衝突。 | A8、D3、D1.1 若分別實作，測試與產品不可能同時滿足。之後必須改 query state、空狀態 UX 與計數。 | 明定三種 query 狀態：raw 空白＝未啟用；raw 非空且產生 ≥1 token＝正常三值比對；raw 非空但產生 0 token＝明確的無有效查詢 token 狀態。並明定此狀態是整體無結果、顯示輸入提示，或其他唯一行為；不得依空集合量詞自行推導。 |
| **Medium** | 名稱條件的真值表只說「子字串」，A9 卻要求小寫 `sodium` 命中，沒有寫明英文大小寫正規化及中文／id 是否同樣處理。 | 搜尋與測試可能各自使用不同正規化，日後會形成瀏覽器差異或只為案例特判。 | 在 D1.1 名稱列明確規定大小寫比較規則與正規化後的比較值。 |
| **High** | **[挑戰既有判定]** 「資產鍵由 id 衍生，因此跨藥錯圖在建構上不可能」不成立。反例：下載器對記錄 A 使用 A 的 key，卻因索引錯位下載記錄 B 的 `src`；C12 仍完全通過，但 A 顯示 B 的圖片。key 只證明命名空間，不能證明內容 provenance。 | 若把 C12 當成充分保證，圖片映射錯誤會直到臨床人工比對時才被發現，且需重建全部圖片 manifest。 | 不需圖片暫存交換；只需在規格上增加 provenance 不變量：每個 `imgs[].src` 必須來自同一 id 的 TFDA 原始圖片欄，檔案實際 sha 必須等於該 `imgs[].sha256`，且來源圖片順序／數量映射須可對帳。 |
| **High** | **[挑戰既有判定]** JSON 最後 rename 只能保證 runner 工作目錄的順序，擋不住「新 JSON＋瀏覽器/CDN 舊圖片」。圖片檔名固定為 id＋序號，原地換圖後 URL 不變，舊快取可繼續命中；這正是威脅模型在意的「新資料配舊圖片」。 | 上線後才改圖片 URL 身分會牽動資料模型、所有既有資產引用與快取策略。 | 不需 Pages-visible 自動驗證，也不需目錄交換；規格上要求圖片內容變更時，其瀏覽器請求 cache key 必須跟著 sha 改變，例如圖片引用含內容版本。最終 commit 仍一次帶入 JSON 與圖片。 |
| **High** | L10 宣稱「暫時性失敗重跑不得重抓已完成圖片」，但 GitHub Actions 失敗 runner 的未提交 `data/img/` 不會自然保留。直接寫正式路徑只對同一持久工作目錄有效，無法保證 Actions 重跑續傳。 | 實作後才發現會重新下載數千張圖，可能撞 L7；屆時需新增跨 run 狀態保存並重做 workflow。 | 明定 L10 適用範圍。若包含 Actions，須規格化「已驗證但未發布圖片」的跨 run checkpoint／artifact；若只要求本機首建續傳，應明說 Actions 失敗重跑可從已發布版本重新開始。這不要求改成目錄原子交換。 |
| **Low** | 「唯一發布點是 rename」用語與資料流不精確。對 Pages 使用者，真正發布點是包含 JSON 與圖片的 commit／deployment；rename 只是提交前 readiness gate。D9 的「已發布內容」則採另一種含義。 | 故障注入位置與「發布前／後」會因術語不一致而誤測。 | 將 rename 稱為「唯一資料就緒切換點」，commit 稱為「唯一對外發布快照」；明定 rename 後、commit 前任何失敗都不得 commit。 |
| **Low** | D 編號順序為 D9、D12、D10、D14、D11、D13、D15、D16。雖無語意衝突，但修訂已使引用與閱讀順序漂移。 | 後續 issue、測試與 PR 引用容易指錯條文。 | 在動工前依編號排序，或保留順序但增加一張決策索引；不要再改決策內容。 |

## 4. 更簡單的替代方案

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **High** | D1.1 以重疊欄位同時描述「條件是否啟用」與「記錄是否缺值」，造成語意複雜且不完備。 | 每個條件都會重複處理相同邊界，測試矩陣膨脹。 | 先做共同的兩階段規則：① 條件未啟用 → match；② 條件啟用 → 依記錄值判三態。imprint 額外先判 query 是否產生有效 token。 |
| **Medium** | D12 把 rename 稱為對外發布交易，卻另靠 commit／Pages 才真正可見，並用 key 不變量承擔它無法證明的內容 provenance。 | 會持續增加針對錯誤抽象層的測試。 | 保留現有三步管線，不新增發布協調者：把 rename 定位為 readiness gate；commit 是對外快照；另以 `src + sha + id` provenance 和圖片內容版本 cache key處理真正剩餘風險。 |

最小動工前修訂範圍是：

1. 補完 D1.1 的條件啟用優先序與零-token query 語意。
2. 撤回「key 可證明不可能跨藥錯圖」的充分性宣稱，補 `id/src/sha` provenance 不變量。
3. 釐清 D12 的 rename、commit 與瀏覽器圖片 cache key 三個層次。
4. 明定圖片例外是逐 `id+src`，以及多圖與恢復情境。

完成上述規格修訂後，其餘 v1.1 架構可沿用，不需要發布協調者、圖片目錄交換、Pages-visible 自動觀測或新後端。
