結論：**目前不宜動工**。有 3 個 Blocker：`SH/HS` 驗收數字與主區歸屬互相矛盾、代表字查詢與雙邊 `canon` 自相衝突、多 token 規則未排除「逐 token 混用兩種變體」而實質違反 N15。以下均為唯讀規格覆審，未修改任何檔案。

# 1. 需求與邊界缺漏

## 1.1 多 token 的「全中」單位未定義

- **嚴重度：Blocker**
- **問題：** D34 只寫「變體全中」，但未說全中必須由同一條規則獨立完成。弱解讀可以讓 token A 靠 `flip`、token B 靠 `canon`，整筆進 `variant`；這實質上就是 N15 禁止的組合變體。也未定義其中一個 token 的 `flip()` 為 `null` 時，是整條倒讀證據失敗，還是略過該 token。
- **為什麼現在不修之後會更貴：** 這會決定 `variant` 的 ID 集合、理由標籤與 oracle 常數。實作後才裁決，搜尋核心、oracle、fixtures、UI 理由與凍結 baseline 都要一起重做。
- **建議修法：** 明定「倒讀」與「字形相近」是兩個**記錄層、規則層**的獨立 predicate；每個 predicate 必須單獨覆蓋全部查詢 token。不得把不同 token 的不同規則命中拼成一次全中。任一查詢 token 無合法倒讀時，整條倒讀 predicate 為 false；`canon` 則仍獨立判定。

## 1.2 `SH/HS` 規格同時有歸屬與數量矛盾

- **嚴重度：Blocker**
- **問題：** A15(a) 寫「查詢 `SH`」時，「真實刻字 `HS` 的 3 筆在主區」，但原樣查詢 `SH` 的主區應是 `SH`，不是 `HS`。以現行搜尋語意對 frozen baseline 實跑：`SH` 為完全／字首／包含 `3/22/12`；`HS` 為 `42/1/1`。此外 D34、B22 明確允許變體字首，因此 `flip('SH')='HS'` 應接住 `HS` 的完全 42 筆及字首 1 筆，候選是 **43**，不是 A15 的 42。
- **為什麼現在不修之後會更貴：** 實作者無法同時滿足 A15(a) 與 B22；無論選哪一個，另一組測試都必紅，最後容易演變成改常數讓測試變綠。
- **建議修法：** 先裁決變體是否允許字首。若沿用 D34/B22，A15(a) 應以 oracle 重算並凍結 43 筆候選，主區敘述改成原樣 `SH` 記錄；若堅持 42，則須明確撤回變體字首，並同步改 D34、B22 與相關非目標邊界。

## 1.3 `canon` 代表字查詢與 A15(e) 衝突

- **嚴重度：Blocker**
- **問題：** D33 規定查詢與記錄雙邊壓平。因此查詢 `0` 雖然 `canon('0')==='0'`，仍應接住記錄 `O`；查詢 `12` 也應接住含 `I/L/Z` 對應字形的記錄。A15(e) 若要求 `0`、`12`「不得產生任何 variant」，便使 `0/O`、`1/I/L`、`2/Z` 變成方向不對稱。按文件的雙邊壓平＋字首規則實跑 baseline，原樣區之外至少分別仍有 **64** 與 **7** 筆 canon 候選。
- **為什麼現在不修之後會更貴：** 這不是測試措辭問題，而是 equivalence relation 是否對稱的核心語意；會改變大量候選 ID 與臨床查詢行為。
- **建議修法：** 把 A15(e) 改成「原樣已命中的同一記錄不得重複進 variant」，而非「代表字查詢不得產生 variant」。另加雙向對照：`0` 可接 `O`、`O` 可接 `0`，但原樣 `0` 記錄仍只在主區。

## 1.4 倒讀的轉換方向只藏在 B22，未寫入決策

- **嚴重度：High**
- **問題：** `flip(tok)` 未明定 `tok` 是查詢 token 或記錄 token。對完全比對兩者因對合而近似等價，但對字首不等價：查詢 `SH` 轉成 `HS` 可字首命中 `HSY`；若轉記錄 `HSY`，因 `Y` 表外會直接是 `null`。
- **為什麼現在不修之後會更貴：** 兩種合理實作會產生不同候選集合；等到 oracle 數字產生後才發現，需重寫規則及所有 expected IDs。
- **建議修法：** 在 D32 明寫「只轉換每個查詢 token，再以完全／字首規則比對原始記錄 token」；B22僅作驗證，不應承擔定義語意的責任。

## 1.5 變體理由的搜尋輸出契約未定義

- **嚴重度：High**
- **問題：** 資料流只寫回傳 `variant`，看起來仍是 item 陣列；但 UI 要求每張卡片知道「倒讀／字形相近／兩者」。規格未定義理由是查詢結果的伴隨資料、ID 對應表，還是會掛回共享 item。若理由寫進 item，連續搜尋可能留下上一個查詢的 stale reason，亦破壞「純函式層」與重入性。
- **為什麼現在不修之後會更貴：** 這是搜尋層與 UI 層之間的資料契約，晚修會同時改搜尋回傳模型、排序、渲染與測試 fixtures。
- **建議修法：** 在規格層明定理由是**每次搜尋產生、query-scoped、不可寫回 canonical/indexed item** 的結果 metadata；同一 ID 最多一筆，理由為互斥集合 `{flip}`、`{canon}` 或 `{flip, canon}`。並定義連續兩次不同查詢不得共享理由狀態。

## 1.6 原樣與變體同時命中不同記錄的全域行為未完整釘死

- **嚴重度：Medium**
- **問題：** D31 定義的是逐記錄優先序，但沒有明確驗收「同一次查詢可以同時有主區與 variant」。A15(a) 原本似乎要擔任此角色，卻寫反了 `SH/HS`。
- **為什麼現在不修之後會更貴：** 弱實作可能只在 `mainCount===0` 時才啟用整批變體，仍符合「原樣比對失敗時」的一種全域解讀，造成主區有候選時漏掉變體區。
- **建議修法：** 明定「原樣失敗」是**逐記錄**而非整次查詢。設具名案例，要求同一次搜尋中原樣記錄留在主區、另一批變體記錄同時出現在第五區。

## 1.7 零 token、單 token、多 token 邊界未形成完整真值表

- **嚴重度：Medium**
- **問題：** 零 token 只在 A13 混入 baseline 案例；單 token 主要測 `S`；多 token 未覆蓋「部分 token 可 flip、部分不可」、「每種規則各中一部分但沒有任何規則全中」。
- **為什麼現在不修之後會更貴：** 這些是最容易因空集合、略過 `null` 或逐 token OR 而錯放候選的分支，錯誤會直接改變臨床結果集。
- **建議修法：** 補一張查詢層真值表：`NO_TOKEN` 永不計算變體；單 token 遵循完全／字首且不得包含；多 token 必須由同一規則全中；任一規則只中部分不得進 variant；兩規則各中不同 token 亦不得進。

## 1.8 其他條件的 mismatch 必須繼續壓過 variant

- **嚴重度：Medium**
- **問題：** `mismatch &gt; variant` 已出現在優先序，但沒有具名案例驗證「imprint 變體全中，但顏色／形狀／刻痕／名稱其中之一 mismatch」仍排除。A14 明示顏色、形狀皆 match，反而避開此風險。
- **為什麼現在不修之後會更貴：** 若變體被實作成提前返回，可能繞過其他 AND 條件，產生大量假陽性。
- **建議修法：** 增加至少一個正交條件 mismatch 的反例及一個 unknown 的優先序案例；前者必須 excluded，後者依 D31 裁決進 variant。

## 1.9 「無新的失敗路徑」陳述過度

- **嚴重度：Low**
- **問題：** 沒有新增 I/O 是事實，但新增了理由 metadata 漂移、重入污染、規則組合誤放行及 UI 狀態漏算等新失敗路徑。
- **為什麼現在不修之後會更貴：** 會使測試計畫錯把新增風險視為不存在。
- **建議修法：** 改成「無新增 I/O／網路失敗路徑；新增的語意與結果契約失敗由 A、B、E、F 組驗證」。

## 1.10 缺少可觀察的效能門檻

- **嚴重度：Medium**
- **問題：** `[新增需求]` 文件只宣稱 6,295 筆可接受，AS14 也只說若有可感延遲再退回 lazy，沒有定義何謂可感。
- **為什麼現在不修之後會更貴：** 上線後若行動裝置輸入延遲或首次載入卡頓，只能憑感覺重選計算時機，連帶改索引策略。
- **建議修法：** `[新增需求]` 設定既有 120 ms debounce 情境下的目標裝置、資料量及搜尋／索引延遲門檻。不做的可觀察後果是使用者輸入後結果更新明顯落後，或初次載入被 `_tokCanon` 阻塞；是否納入由使用者裁決。

# 2. 架構風險

## 2.1 與既有平台限制沒有直接衝突

- **嚴重度：Low**
- **問題：** D30–D36 本身不需要後端、依賴、build step、AI、分數或 JSON 衍生欄，與已聲明限制相容。
- **為什麼現在不修之後會更貴：** 此項不是缺陷，但若後續為理由 metadata 引入持久化欄位，會撞 D15。
- **建議修法：** 保留純靜態、線性掃描、記憶體衍生與無分數設計；規格明示 query-scoped 理由不得持久化，即可維持相容。

## 2.2 最難回頭的是「雙邊 canon＋字首放行」的 admission policy

- **嚴重度：High**
- **問題：** 最難回頭的不是第五區 UI，也不是 `_tokCanon` 放哪裡，而是 D33 與 D34 合併後形成的等價類＋字首規則。它會一次擴張大量候選，並凍結成 oracle ID sets。
- **為什麼現在不修之後會更貴：** 規則一上線便成為使用者心智模型；日後縮表或撤回字首會造成同一查詢候選突然消失，需同步改文件、oracle、測試與臨床說明。
- **建議修法：** 動工前以具名查詢凍結每條規則的獨立候選 ID、交集 ID、區內排序與理由集合；不要只凍結總數。

## 2.3 五個互斥區無法同時表達正交的不確定來源

- **嚴重度：Medium**
- **問題：** 一筆記錄可能同時是 imprint variant，且顏色 unknown。D31 選擇 `variant &gt; unknown`，因此分區名稱只揭露刻字假設，資料缺值資訊只能靠卡片內容間接看出。
- **為什麼現在不修之後會更貴：** 未來若要解釋「為何不能排除」，單一 bucket 已丟失另一個條件狀態，需要擴充結果 metadata。
- **建議修法：** 不必新增第六區；但規格應明定 bucket 是主要原因，而結果仍保留所有已啟用條件的狀態供稽核。若拒絕保留，需明確接受「variant 區不完整揭露其他 unknown 原因」的取捨。

## 2.4 `indexItems()` 的既有 mutation 與「純函式層」措辭不一致

- **嚴重度：Low**
- **問題：** 現行 `indexItems()` 已把 `_tok` 掛回 item；新增 `_tokCanon` 也會 mutation。真正必須純的是搜尋結果與理由不能污染跨查詢狀態。
- **為什麼現在不修之後會更貴：** 若把「純函式」誤解成所有物件皆 immutable，可能不必要地改既有架構；反之若完全忽略純度，理由可能被寫回 item。
- **建議修法：** 將限制改寫為「索引階段允許一次性記憶體衍生；搜尋階段不得修改 indexed item，結果與理由須可重入」。

# 3. 驗證策略缺口

## A13

- **嚴重度：High**
- **問題：** 現有 `[堵死]` 只堵住「變體永遠空」及既有區互換；仍有弱實作可從 excluded 任意挑 N 筆塞進 variant，同時減少 excluded，完全通過恆等式。≥12 組 criteria 也未全部具名。「功能停用時」的 baseline 來源未定義，且 N18 又拒絕產品開關。
- **為什麼現在不修之後會更貴：** A13 是全量 regression 主護欄；若只驗守恆不驗身份，錯放藥品仍全綠。
- **建議修法：** 每個具名 query 同時比對：既有各區 ordered IDs、variant ordered IDs、每個 variant ID 的理由集合及 excludedCount。停用前 baseline 應明定為已凍結 expected manifest，不新增產品功能旗標。12 組全部列名，不使用「≥12」留下自由替換空間。

## A14

- **嚴重度：Medium**
- **問題：** `[堵死]` 有效，但只覆蓋 exact MATCH、一般 PARTIAL、UNKNOWN；弱實作仍可把 PREFIX／CONTAINS 原樣命中搶進 variant，或只有在其他條件 unknown/mismatch 時提早返回 variant。也未驗證 `NO_TOKEN`。
- **為什麼現在不修之後會更貴：** 會破壞「只由 imprint MISMATCH 產生」的完整性，且 A13 不一定遇到這些組合。
- **建議修法：** 對 imprint 的 OFF、NO_TOKEN、UNKNOWN、MATCH-EXACT、MATCH-PREFIX、MATCH-CONTAINS、PARTIAL、MISMATCH 建立具名分類矩陣；再與一個其他條件 MATCH／UNKNOWN／MISMATCH 交叉驗證關鍵格。

## A15

- **嚴重度：Blocker**
- **問題：** `[堵死]` 尚未成立：
  - (a) `SH/HS` 主區文字寫反，且 42 與 B22 的字首放行衝突。
  - (b) 「S/5 的 291 筆」是影響規模，不是具體 query 的 variant 驗收數；「落在 variant 者」允許 variant 為空而真空通過。
  - (c) 未窮舉所有 fixed point；`69`、`MW` 等也可能 `flip(s)===s`。
  - (d) 只要求沒有倒讀理由，需避免被誤讀成整個 variant 必須空。
  - (e) 與雙邊 canon 衝突。
  - (f) 未指定 fixture token，無法確保兩個理由是各自全中，而非組合後才全中。
- **為什麼現在不修之後會更貴：** A15 同時承擔正例、反例與人工裁決；目前會逼出互斥實作。
- **建議修法：** 重寫六項：
  - (a) 由 oracle 凍結正確的 `SH` 主區與 `HS` 變體 ID sets，裁決是否含字首。
  - (b) 指定 `S` 的精確 variant IDs／數量，不引用 291 上界。
  - (c) 對所有實際 token 中 `flip(t)===t` 者驗證不會因 flip 進 variant。
  - (d) 斷言 reason 不含 `flip`，而非 variant 整區為空。
  - (e) 改驗「原樣記錄不重複」，另測代表字雙向接住對側字形。
  - (f) 明定例如一個記錄含兩個 token，且 flip、canon 各自獨立全中；另加「各中一部分」的否定對照。

## A16

- **嚴重度：Medium**
- **問題：** 雙向斷言堵住「永不 EMPTY」，但若只手工構造 result object，弱實作可以讓 `search()` 永遠不產生 variant，而 `resultStates()` 對假資料仍通過。
- **為什麼現在不修之後會更貴：** UI 最危險的錯誤正是實際搜尋與狀態推導未接通。
- **建議修法：** 第一條必須由實際 fixture 經 `search()` 產生「僅 variant 有值」的結果，再送入 `resultStates()`；第二條使用同一 fixture 的反例查詢產生真正全空結果。另斷言兩者 UI 文案分支。

## B20

- **嚴重度：Medium**
- **問題：** 對合只驗長度 1–3，長 token 的 reverse bug 可存活；對合也不能證明映射正確，例如錯把兩個自映射字互換仍是對合。≥20 個表外案例未保證覆蓋所有 22 個表外英數字元及首／中／尾位置。
- **為什麼現在不修之後會更貴：** `flip` 是 oracle 與 production 共用的規格核心；錯一個字元會靜默改候選。
- **建議修法：** 獨立逐字斷言完整 14 字元映射；對所有其餘 `[A-Z0-9]` 字元驗首／中／尾表外即 `null`；對實際 token 全量驗對合，並保留至少一個長度大於 3 的具名向量。

## B21

- **嚴重度：Medium**
- **問題：** 冪等＋值域＋三個向量仍允許錯映射，例如 `Z` 被刪除或映成 `8`；目前向量沒有逐一釘死五個 class 的所有成員，也沒驗證 class 外字元保持不變。
- **為什麼現在不修之後會更貴：** identity 以外仍有大量錯誤 canonicalizer 可通過，造成不可預期碰撞。
- **建議修法：** 逐字驗證五個 equivalence class 的每個成員都映到指定代表字，並對其餘 `[A-Z0-9]` 全部驗 identity；再保留實際 token 全量的冪等與值域斷言。

## B22

- **嚴重度：High**
- **問題：** 單 token 的正反例可堵住「功能沒接上」與 contains，但弱實作可在多 token 時重新允許 contains，或讓不同 token 分別靠 flip/canon 後拼成全中。
- **為什麼現在不修之後會更貴：** 這直接打開 N15/N16 所稱的笛卡兒積入口。
- **建議修法：** 加入多 token 對照：任一 token 只能 contains 時整條規則失敗；同一規則全部 exact/prefix 才成功；flip 與 canon 各中不同 token 時仍失敗；兩規則各自全中時才顯示雙理由。

## C20

- **嚴重度：High**
- **問題：**
  - 靜態斷言只禁兩個特定字串，改用 `../search.js`、dynamic import、re-export 或不同相對路徑即可繞過。
  - 只要求硬編 variant 筆數，沒有要求 production 結果逐筆對 oracle 的 variant IDs／理由。
  - 移除 `M↔W` 是否讓 `npm run expected` 失敗，取決於 ≥6 個查詢中是否真的有非零且敏感的 M/W 案例；目前未具名。
  - 即使 oracle 變異會失敗，也不代表 production 同類變異會被 expected manifest 殺死。
- **為什麼現在不修之後會更貴：** oracle 看似獨立但可能只在數量上自洽，兩邊錯放同數量的不同藥仍全綠。
- **建議修法：** 禁止任何解析後指向 `search.js` 的 import/re-export；oracle 輸出每個具名 query 的 ordered IDs 與理由集合；至少具名包含 M/W、5/S、表外字元、fixed point、multi-token no-composition、雙理由六類；oracle 與 production 分別施加規則變異並要求 manifest 對帳失敗。

## E12

- **嚴重度：Medium**
- **問題：** 「全區 DOM 不得出現」若只是掃原始碼或整頁文字，無法證明理由貼在正確卡片；固定把兩個詞放在區標題，也可能讓雙理由案例通過。A15(a) 的 42 筆本身又是錯誤基準。
- **為什麼現在不修之後會更貴：** 搜尋結果正確但理由貼錯卡，使用者仍會被錯誤陳述誤導。
- **建議修法：** 對實際渲染後的 variant section 定位每張卡片，以 ID 對照 expected reason set；單理由卡不得含另一理由，雙理由卡必須同卡同時含兩詞。百分比等禁語只掃該區可見文字。先修正 A15(a) 的 ID set。

## F13-1

- **嚴重度：Medium**
- **問題：** A14(b)(c) 只有在 fixtures 的變體確實會命中時才殺得掉移除 MISMATCH guard；目前未指定 token，可能 mutation 存活。
- **為什麼現在不修之後會更貴：** mutation 表會宣稱覆蓋但實際沒有觸發被刪條件。
- **建議修法：** 具名指定原樣 PARTIAL／MATCH 且變體 predicate 亦為 true 的 fixtures，確認移除 guard 必定改 bucket。

## F13-2

- **嚴重度：Medium**
- **問題：** A13 只有資料中實際存在「imprint variant＋其他條件 UNKNOWN」交集時才會紅；≥12 組未保證有此交集。
- **為什麼現在不修之後會更貴：** 優先序錯誤可在目前 baseline 偶然沒有交集時存活。
- **建議修法：** 使用明確 fixture 同時產生 VARIANT 與 UNKNOWN，直接斷言依 D31 進 variant，且不得進 unknown。

## F13-3

- **嚴重度：Medium**
- **問題：** B20 的 `MW` 向量可殺 production mutation；但 C20-3 不保證 oracle mutation 會失敗，因未要求具名 M/W expected query。
- **為什麼現在不修之後會更貴：** oracle 的 M/W 分支可能完全未被任何自檢消費。
- **建議修法：** C20 強制包含一個移除 M/W 後 variant IDs 必改變的具名 query。

## F13-4

- **嚴重度：Medium**
- **問題：** B21 的 `SILO` 可殺 mapping mutation；A15(b) 的「落在 variant 者」卻可由空集合真空通過，不能如表中宣稱殺死它。
- **為什麼現在不修之後會更貴：** mutation 與預期紅燈對應不實，測試維護者會誤判保護範圍。
- **建議修法：** A15(b) 必須凍結非零的精確 variant ID set，並要求移除 5/S 後對帳失敗。

## F13-5

- **嚴重度：High**
- **問題：** 「A15 筆數、C20-2」不保證含多 token 只部分變體命中的查詢；現有 A15 沒有明確這類 fixture，C20 也只要求任意 ≥6 查詢。
- **為什麼現在不修之後會更貴：** 變體 PARTIAL 放行正是 N16 明確拒絕的假陽性入口。
- **建議修法：** 強制一個具名多 token query：只有部分 token 由 flip 命中、另一個只有部分由 canon 命中，兩條規則均不得放行；其 variant expected set 必為空。

## F13-6

- **嚴重度：Medium**
- **問題：** A16 若只使用手工 result 可殺 `resultStates` mutation，但不能驗證 UI 確實使用該狀態及實際搜尋能產生它。
- **為什麼現在不修之後會更貴：** 核心狀態正確、UI 分支沒接上時仍會顯示「找不到」。
- **建議修法：** A16 使用搜尋整合 fixture，E12 增加只有 variant 時不得渲染 EMPTY 文案。

## F13-7

- **嚴重度：Medium**
- **問題：** B22 只涵蓋單 token；弱 mutation 若只對多 token 開啟 contains 可存活。
- **為什麼現在不修之後會更貴：** 多 token 查詢更常觸發高基數假陽性。
- **建議修法：** B22 加入多 token 中一個 token 僅 contains 的反例。

## F13-8

- **嚴重度：Low**
- **問題：** B20 第二條確實能堵住「表外回原字串」，但 ≥20 未具名，可能 fixture 沒包含 mutation 影響的實際位置。
- **為什麼現在不修之後會更貴：** 測試資料若被任意替換，仍可能失去守門力。
- **建議修法：** 改成所有表外英數字元 × 首／中／尾位置的系統性斷言；保留 `OST` 具名案例。

# 4. 更簡單的替代方案

## 4.1 先只上線一條規則會衝突目前目標

- **嚴重度：High**
- **問題：** 只做倒讀或只做 canon，會直接違反目標 1「額外嘗試兩種確定性變體」，不是相容的規格簡化。
- **為什麼現在不修之後會更貴：** 若未先改目標便分期，第一期到底算完成或未完成會沒有一致驗收基準。
- **建議修法：** 若使用者要分期，必須明確裁決變更目標與里程碑；否則本版仍應同時納入兩條規則。

## 4.2 「先上線觀察」在現有威脅模型下沒有觀察資料

- **嚴重度：Medium**
- **問題：** 專案無 analytics、cookies、使用者狀態，也不傳輸查詢；因此先上線一條並不能得知它是否真的幫助藥師，最多只能觀察主觀回報。
- **為什麼現在不修之後會更貴：** 可能以「分期觀察」為名延後另一條規則，但實際沒有可裁決的觀察指標。
- **建議修法：** `[新增需求]` 若選分期，先定義不進產品、不收病患資料的離線臨床案例評讀或人工回饋方法及停止條件。不做的可觀察後果是上線後沒有任何資料能決定第二條是否應加入。是否接受此新增需求由使用者裁決。

## 4.3 相容且更簡單的方案是收斂成一份 admission contract

- **嚴重度：Medium**
- **問題：** 現文件把相同邊界散落在 D31、D34、N15、N16、A14、B22；尤其「MISMATCH 才算、同一規則全中、完全或字首、不得跨規則拼接」沒有單一權威定義。
- **為什麼現在不修之後會更貴：** production、oracle 與測試各自從不同段落拼語意，最容易形成三份近似但不同的規則。
- **建議修法：** 保留一個 variant bucket 與兩個獨立理由，但用一張完整 admission truth table 作為唯一語意來源；其他章節只引用它。這不增加元件，也不改平台架構。

## 4.4 第五區本身不是 over-engineering

- **嚴重度：Low**
- **問題：** 在 F8 禁止分數、且既有四區不得移動的前提下，獨立第五區是最小的可稽核表示；混入主區或引入評分都會撞已聲明限制。
- **為什麼現在不修之後會更貴：** 若為了表面簡化而取消第五區，會失去事實命中與假設命中的可見邊界。
- **建議修法：** 保留第五區；簡化應發生在 admission contract 與理由資料契約，不應合併結果區或改用分數。

最終裁決：**先修正三個 Blocker，再產生任何 expected IDs／常數；目前版本不可進入實作。**
