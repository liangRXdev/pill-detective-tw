| **Medium** | **來源請求只定義非 200／非法 ZIP，未定義 timeout、redirect、截斷下載及超大回應。** | 失敗可能拖到 Actions 6 小時上限，或先耗盡磁碟／記憶體才失敗。 | `[新增需求]` 規定來源與圖片下載的有限 timeout、redirect 政策及合理大小上限。**不做的可觀察後果：**workflow 長時間卡住而非及早保留上一版。這與 L1–L9 不衝突。 |

| **Low** | `meta.vocab:{color,shape,score}` 中 `score` 實際代表刻痕，容易與排名分數混淆。 | 後續很可能被誤讀為禁止的 confidence score。 | 規格改名為 `mark`、`scoreLine` 或明確的 `scoring` 以外名稱；全文件一致。 |

## 區塊 2：架構風險

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **Blocker** | **目前的 `.tmp + rename` 無法提供整個 `data/` 的全有全無。** 單檔 rename 只能保護單檔；appearance、多張圖片及 hash 回填之間仍有中間狀態。§6 更像先 rename `appearance.json`，之後才抓圖，與 C10「兩份都維持前版」矛盾。 | 完成後才發現會牽動所有產物路徑、增量基線、失敗回復及測試 fixture。 | 在規格層定義「發布交易邊界」與「使用者可見版本切換點」，並要求在切換前所有新產物均不可取代前版。替代作法必須保留「從正式輸出路徑讀前版 hash」，避免與刻意限制 (a)4 衝突；不能籠統改用 `$RUNNER_TEMP` staging。 |
| **Blocker** | **圖片 URL 未變即永遠沿用舊 hash，無法偵測官方原地換圖。** 這正是威脅模型第 3 項，但 C11 把「URL 未變→不抓」寫成永久規則。無 ETag／Last-Modified 時，URL 不等於內容不變。 | 一旦錯圖累積，只有全量重抓及重新比對才能發現；現有 `src_sha256` 只證明曾下載什麼，不能證明目前官方仍是什麼。 | `[新增需求]` 定義可控的內容重新驗證週期或人工全量稽核程序，且差異須與同版 appearance 一起發布。**不做的可觀察後果：**官方在相同 URL 換圖後，本站永久顯示舊圖，與目前 TFDA 資料不一致。此替代作法不能放入每週 workflow 若會撞 L7；可採較低頻、分批但發布仍全有全無的維護流程。 |
| **High** | **圖片建立過程可能先覆寫正式檔，再於後續圖片失敗。** 因資產鍵依許可證固定，URL 變更時新圖可能覆蓋舊檔；appearance 尚是舊版時就形成「舊資料配新圖」。 | 這是威脅模型明列的高風險失效；完成後需重做圖片產物生命週期。 | 規格明定待發布圖片在交易提交前不得改寫任何正式圖片；失敗後正式圖、manifest、mtime 與多餘檔案集合都必須維持前版。 |
| **High** | **永久性壞圖沒有裁決路徑。** 任何非空官方 URL 若永久回 0 bytes，整個資料更新會永久紅燈；但 F4 又允許 placeholder。 | 第一次遇到永久性壞連結就無法再發布任何其他合法更新。 | `[新增需求]` 定義經人工裁決後可將特定官方圖記錄為「官方暫無可用圖片」的受審例外，保留來源 URL 與理由；不得由暫時性網路失敗自動降級。**不做的可觀察後果：**單張永久壞圖會讓全站資料無限期停留在舊版。 |
| **High** | **最難回頭的決策不是 static/vanilla，而是三值候選模型與跨檔發布交易。** 前者決定所有搜尋結果，後者決定是否可能出現錯圖標示。 | 兩者都橫跨資料模型、核心搜尋、UI 與測試。 | 動工前先把 tri-state truth table、各搜尋欄位的 unknown 規則、發布狀態機與檔案集合不變量寫成規格表。 |
| **Medium** | **D6 只鎖資料詞彙，沒有保證 UI chips 與 lock 完全相等。** 管線可接受 13 個值，但 UI 少一個、拼錯一個或多一個都可能照樣發布。 | UI 完成後才發現需再建立資料與畫面的契約。 | 增加既有 D6 的驗收：顏色／形狀／刻痕可選值集合必須與 `vocab.lock` 完全相等，不只是數量相等。這是驗證既有需求，不是新增需求。 |
| **Medium** | **`mtok`、`ntok` 是可由 raw 欄位衍生的持久化資料，增加 schema 漂移面。** 同一 normalizer 雖可降低實作漂移，仍可能出現 raw 更新但衍生欄未同步。 | 發布格式被外部消費後再移除或改義會有 schema 成本。 | 較簡單的規格方案是僅保存 canonical raw/cleaned fields，載入後用同一份 `search.js` 建立記憶體索引；若保留衍生欄，必須規定 verifier 逐筆重算並要求完全相等。 |
| **Medium** | **`content_hash` 的涵蓋範圍與序列化方式未定義。** 是否包含 meta、圖片 hash、陣列順序、空值形式都不清楚。 | 後續任何格式微調都可能造成假變更或漏變更，破壞增量與冪等。 | 明定 hash 對象、canonical serialization、欄位順序、文字編碼，以及是否排除 `content_hash` 本身。 |
| **Low** | F10 要求 `build` 通過，但 L2 明定無 build step。 | 容易為通過文字驗收而加入空的 build script。 | 改成「在乾淨 checkout 中，資料驗證與全部測試通過；本專案無前端 build step」。 |
| **Low** | D8 的「警告」沒有指定後續週更是否可一直忽略。 | 新欄位可能長期有值但 UI 永遠未裁決。 | 規格要求 warning 必須包含非空筆數、代表值及欄位名；是否提升為 blocker 由人工另行裁決，不自動新增 UI。 |

平台相容性結論：static、零前端依賴、線性掃描、官方圖鏡像及不用 CSS 幾何假測試都合理，沒有必要改成 framework、backend、搜尋函式庫或 jsdom。真正架構缺口集中在 tri-state semantics、跨檔交易與圖片內容新鮮度。

## 區塊 3：驗證策略缺口

### 3.1 跨條件的驗證問題

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **Blocker** | A1 與 A3 對「三級筆數」採不同口徑。A1 的 72／129／67 是互斥區；A3 的 95／428／950 看起來是巢狀累計。若 UI 三區互斥，`T` 應是 95／333／522。 | 同一搜尋結果不可能同時符合兩種分區定義。 | 明定所有三級數字都是互斥區或累計集合。依 D3 的 UI 描述，建議全改互斥，並驗證三區 pairwise disjoint。 |

| A7 | Medium | 只特判一筆 `白;;;紅`；錯誤地讓所有多色藥命中任何顏色仍可漏測。 | 多值欄位會普遍錯誤。 | 對固定 fixture 中所有多色案例驗證每個存在值皆命中、至少一個不存在值不命中，並驗證不因重複 token 產生重複卡片。 |

## 區塊 4：更簡單的替代方案

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **High** | 目前不是「元件太多」的 over-engineering，而是交易責任分散：Node 產 appearance、Python 改圖片與回填、Node verify，再期待多檔原子性。 | 各階段都能碰正式產物時，失敗矩陣快速膨脹。 | 保留 Node＋Python 與 L9，但在規格上設一個唯一的發布協調者；其他步驟只產生候選結果，只有協調者能切換正式版本。不得改成 `$RUNNER_TEMP` 並失去正式路徑的前版 hash。 |
| **Medium** | `mtok`、`ntok`、raw 欄位及三組圖片平行陣列，使 canonical JSON 同時承擔來源保存、搜尋索引與圖片 manifest。 | 任一規則改變都可能要求 schema migration。 | 更簡單的方案是 canonical 只保存必要來源／顯示資料與逐圖具名記錄；搜尋衍生 token 在載入時由唯一 `search.js` 生成。6,295 筆規模與 L1、L2、D11 相容。若保留預算欄，則 verifier 必須逐筆重算。 |
| **Medium** | A 組大量依賴全量即時資料的精確 count，維護成本高且與週更衝突。 | 每次合法資料更新都要人工判斷大量數字變更。 | 採兩層：凍結 baseline 驗證精確 count/ID sets；20 筆人工 fixture 驗證髒值轉換；live 週更只驗證不變量與守門。這比每週改全量常數簡單且可證偽。 |
| **Low** | D8 的兩個永久空欄位保存在 UI-facing JSON，只為 audit，會增加 schema 與 payload，但目前沒有 UI 使用者。 | 未來容易被誤當成已支援欄位。 | 若「全量 canonical」只指目前目標欄位，可將它們留在管線 schema 監測而不輸出到前端 JSON；若 audit 必須離線保留，則明確標示非 UI schema。此項涉及既有 D8 取捨，應由使用者裁決，不預設刪除。 |
| **Low** | `package.json` 中的 `build`、可能的 lint 與零依賴主張容易形成形式性腳本。 | 空腳本增加維護噪音。 | 只保留有實質 assertion 的 `test`／data verification 指令；語法檢查若由 Node 原生能力完成，直接列為驗收步驟，不需虛構 build pipeline。 |

### 總結裁決

目前有三項應在動工前解決：

1. **統一 D1 三值邏輯，修正 A6、A10。**
2. **統一 imprint 三級計數口徑，修正 A3。**
3. **定義跨 appearance／圖片／hash 的真正發布交易，並處理 URL 不變但圖片內容改變的風險。**

其餘 static、vanilla JS、零前端依賴、全量線性掃描、圖片鏡像、CSS 採人工瀏覽器驗收等取捨均與 §4 相容，沒有理由改成 framework、backend、搜尋函式庫或 jsdom。
