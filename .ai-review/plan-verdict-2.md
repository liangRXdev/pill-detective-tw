## 事實查核（判定前先實跑／實查）

| 查核項 | 結果 |
|---|---|
| **D1.1 的重疊是否影響已算出的數字** | **不影響。** 產生 §10 全部數字的腳本本來就是「條件未啟用 → 直接 match，不看記錄值」（`!sel.length ? MATCH : …`、`qt` 為空即 return MATCH）。Codex 指出的是**規格文字**的歧義，不是數字錯誤。v1.2 只需把腳本已隱含的優先序寫進真值表，A 組數字全部維持 |
| **零 token 查詢的實際行為** | **確認為未定義。** 依 v1.1 的「每個 Q token 皆命中」，`無` 產生零 token → 量詞在空集合上真空成立 → **所有有 token 的記錄都會 match**，與 A8 正面衝突。Codex 完全正確，這是我漏掉的組合 |
| **A11 的 3,868** | **已實跑確認**（顏色白＋黃 → 主區 3,868、未提供區 217）。Codex 說「未出現在第一輪查核表」屬實——那是我的落檔疏漏，非數字有誤 |
| **baseline 的外部錨點** | 本次下載的 ZIP sha256 = `25b817baea5236b6e5ef14a2bdb70c00e583b79679465722c111b82874086015`，與姊妹專案 2026-08-10 落檔的 `content_hash` **完全相同**。佐證：(a) 來源 ZIP 位元組跨次下載穩定，可作版本識別；(b) 08-10 至今來源未變。此 hash 可作為 D13 要求的外部錨點 |
| **C12 的反例是否成立** | **成立。** 我的 v1.1 只斷言「檔名的 key 段 === sha1(id)」。若下載器把 A 的 key 配上 B 的 `src`，該斷言照樣全過而畫面是跨藥錯圖。**我第一輪「跨藥錯圖在建構上不可能」的宣稱過強** |
| **瀏覽器快取的錯配是否成立** | **成立。** 檔名固定為 `sha1(id)-n.webp`，TFDA 原地換圖後我方檔案內容變、URL 不變，已快取的瀏覽器會繼續顯示舊圖。GitHub Pages 對靜態資產給的是可快取回應，這條路徑我完全沒防 |
| **L10 在 Actions 上是否成立** | **不成立。** Actions runner 是短暫的，失敗 run 未提交的 `data/img/` 不會保留。L10 的續傳實際只在本機持久工作目錄成立 |

### 區塊 2：架構風險

| # | 項目 | 嚴重度 | 判定 | 理由 |
|---|---|---|---|---|
| S7 | **D1.1 各列非互斥（未啟用 vs 記錄缺值）** | **Blocker** | **接受** | 屬實。雖然產生數字的腳本已隱含正確優先序（見事實查核），但規格文字容許另一種合法解讀，而兩種解讀的初始畫面與未提供區完全不同。改為兩階段：① 條件未啟用 → `match`，**不查看記錄值**；② 已啟用才判三態 |

## 結論

**可以動工**（v1.2 修訂完成後）。

理由：本輪兩項 Blocker 都是**語意補完**——一項的正確行為早已隱含在產生驗收數字的腳本裡，
另一項是新增一個先前無定義的狀態；兩者都**不改變已審過的搜尋模型、資料流或發布架構**，
§10 的全部數字維持不變。兩項 [挑戰既有判定]（provenance、cache key）
以**新增斷言與一個 `?v=` 慣例**解決，同樣不動架構。

依本指令「Blocker／High 若導致架構整段更動才需重跑」的條件，本輪不符合，
**不建議跑第三輪**。剩餘風險已由 `/codex-review` 的區塊 4（規格符合度稽核）承接——
本專案的真正缺口從來不是規格再審，而是「規格寫對了、實作做了弱化版」的那道縫。
