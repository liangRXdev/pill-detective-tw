## 事實查核（判定前先驗，不採信任何未經實跑的數字）

Codex 本輪提出三項需要實跑才能判真偽的主張。**三項全部驗證屬實**：

| # | Codex 主張 | 主持人實跑 | 結論 |
|---|---|---|---|
| 1 | 查詢 `Y5P` 產生 **111 筆** variant，且 `Y5P` 不在 2,357 個真實 token 中 | canon 類 `Y5P` 含真實 token `YSP`，記錄 **111 筆**；`Y5P` 本身非真實 token，原樣命中 0 筆 → 變體區 **111** | **屬實** |
| 2 | F13-4：移除 `5/S` 不會改變查詢 `10` 的結果 | 查詢 `10` 的 canon 類成員只有 `10`、`LO`，**含 `5` 或 `S` 的成員 0 個** | **屬實**（我的 F13-4 對應寫錯）|
| 3 | F13-10：`M 40` 不是逐 token OR 的 witness | 有 token `W` 的記錄 49 筆、canon 為 `40` 的記錄 24 筆，**交集 0 筆** → 逐 token OR 變異下 `M 40` 仍為 0 | **屬實** |

**主持人另行掃完整個可達查詢閉包**（3,103 個查詢，含 flip／canon 導出的非真實 token）：

```
最壞變體區 111 筆（查詢 Y5P）｜flip predicate 上界 84（查詢 W）｜canon predicate 上界 111
「真實 token 當查詢」的最壞值只有 84 —— A17 的母體確實漏掉了更壞的情況
```

**Codex 沒說的一件事**：>100 的案例全部是同一個模式——

| 查詢 | 對應真實刻字 | 筆數 |
|---|---|---|
| `Y5P` | `YSP`（永信）| 111 |
| `5T` | `ST` | 96 |
| `5TD` | `STD` | 81 |
| `5YN` | `SYN` | 64 |

**全部是「把廠商前綴的 `S` 看成 `5`」——這正是本功能要解決的情境。** 111 不是規則失控，是正確答案。
這個觀察改變了 S1 的修法方向（見下）。

**F13-10 的真實 witness 已找到**（Codex 只說缺，沒找）：
查詢 `W L30` vs 記錄 `衛署藥製字第034807號`（token `M, T, 130, HOPER`）。
`W` 靠倒讀命中 `M`、`L30` 靠字形命中 `130`，但 `flip('L30')` 因 `L` 表外回 `null`（倒讀整條 false）、`W` 為單字元（字形整條 false）→ 兩條規則都不全中，**正確排除**。逐 token OR 變異下會被誤放行。

## S1／A17：唯一的 Blocker，判定 **部分接受**

- **問題屬實（Blocker）**：A17 的查詢母體是「2,357 個真實 token」，而使用者輸入空間遠大於此。
  `Y5P` 是合法輸入、可達 111 筆、卻不在母體內。**我在第一輪引入 A17 時把「真實 token 樣本」外推成「完整合法查詢域」——這是取樣偏誤，與我自己在 A15 [堵死] 段批評 v0.1 的錯誤是同一類。**

- **接受**：查詢域必須改成**完整可達查詢閉包**（由資料 token 經 `flip`／`canon` 關係導出，含非真實 token 的代表字）。

- **不採用 Codex 的修法**（保留「>100」政策 gate 並縮規則使 111 落到線下）。理由三條：
  1. **>100 的四個案例全都是本功能的目標情境**（`S`→`5` 的廠商前綴誤讀）。唯一能壓下它們的規則是「canon 類記錄數超過門檻時整條 predicate 停用」——那會讓 YSP／ST／STD／SYN 這些**最常見**的誤讀情境反而查不到，等於用漏檢換清單長度，直接違反 D1。
  2. **調高常數到 111 以上是 repo 明令禁止的「改常數讓測試變綠」**，且 AS16 已寫明「若實際門檻更低，常數要下修而非上修」。
  3. 絕對上界原本是我在第一輪用來壓制 801 筆的**設計逼迫工具**。801 是壞規則造成的；規則收緊後（D34 撤回字首、D33 單字元不做字形）最壞值降到 111，**逼迫工具已經完成任務**，把它留作永久 release gate 是錯的工具。這一點 Codex 自己也說了（§4「A17 目前同時不足且過頭」）。

- **使用者裁決（2026-08-14）**：「111 筆在預設收合、標題顯示筆數的分區裡，藥車前可接受」→ **放棄絕對上界**。

- **修法（v0.3）**：
  - **A17 改為「可達查詢閉包的規則指紋」**：凍結三個數字（最壞 111／flip 上界 84／canon 上界 111），**任一變動即紅**。它守的是**規則漂移**，不是政策門檻。
    實測驗證它仍能抓住原本要抓的：F13-7（放行字首級）→ 閉包最壞值上升 → 紅；F13-12（單字元啟用字形）→ 查 `I` 801 筆 → 紅。
  - **新增 C21（發布守門，對待發布資料動態重算）**：`verify-data` 執行同一套閉包掃描（853 ms），**與前一版指紋比對，顯著上升時 fail-closed 要求人工裁決**，不綁絕對常數。這解決 Codex §2 指出的生命週期問題：baseline 守規則、C21 守資料。
  - **規模的臨床防護回到既有機制**：預設收合 ＋ 標題顯示筆數 ＋ 既有 §8.4 的「候選過多」提示。
  - **p99 降為報告指標，不列為 gate**（採 Codex §4 建議 4）。

## 結論

**可以動工。**

理由：

1. 第一輪 4 個 Blocker 中 3 個經獨立驗證為修訂充分；第 4 個（S1）的問題屬實但**不需要改架構**——它改的是 A17 這條驗收的查詢域與性質，以及新增一條發布守門（C21）。admission contract 本體（§5）、D30–D37、其餘驗收全部不動。
2. 本輪**零範圍蔓延、零拒絕**，且 Codex 明確判定 A13／A16／B21／B22 的 `[堵死]` 成立、1.1／1.2 修訂充分。
3. 本輪所有修訂都是**驗收層**（查詢域、witness 具名、斷言補強），不是架構層。依 `/codex-checkplan` 的規則，只有「Blocker 或 High 導致架構整段更動」才需要再重審——本輪不符合該條件。

下一步（實作順序不變）：
`search.js`（flip／canon／`Cond.VARIANT`／`resultStates`／結果契約）→ `make-expected.mjs` 獨立雙實作 → UI 新區 → 測試 → `verify-data` 的 C21 守門。
