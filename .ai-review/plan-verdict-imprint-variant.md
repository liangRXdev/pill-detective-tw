## S1（主持人自查，Codex 未發現）　變體區最壞膨脹到 801 筆

- **嚴重度：Blocker**
- **問題**：規格 v0.1 的 D34 只停用「包含」級、放行「字首」級，且 D33 對單字元查詢也啟用字形壓平。
  拿全部 2,357 個真實 token 各自當查詢實跑，變體區筆數：

  | 規則 | 中位 | p90 | p99 | 最大 | >100 筆的查詢 |
  |---|---|---|---|---|---|
  | 規格 v0.1 | 0 | 2 | 66 | **801**（查 `I`）| 15 個 |
  | 單字元不做字形變體 | 0 | 1 | 42 | 234 | 7 個 |
  | ＋單字元倒讀只用完全級 | 0 | 1 | 40 | 206 | 4 個 |
  | **採用：變體一律只接受「完全相等」** | 0 | **1** | **12** | **84** | **0 個** |

  查 `I` → 801 筆、`5` → 768 筆、`L` → 643 筆。**這是威脅模型第 2 條「假陽性淹沒真陽性」的教科書案例**，
  且 v0.1 自己的 [堵死] 段沒有任何一條驗收會抓到它——所有斷言都在驗「該中的有沒有中」，
  沒有一條在驗「變體區會不會大到不可用」。
- **為什麼現在不修之後會更貴**：這是 Codex 2.2 所稱「最難回頭」的 admission policy 本體。上線後縮表會讓同一查詢的候選突然消失。
- **修法**：
  - **D34 改為：變體比對只接受 token 完全相等**，不啟用字首級、不啟用包含級。
  - **D33 補充：單字元查詢不啟用字形變體**（單字元壓平＝「刻字第一個字母像 5」，與 D18 判定不可用的包含級同性質）。**單字元的倒讀保留**——把藥翻過來 `6` 變 `9` 是真實物理情境，實測查 `6` 只多 10 筆、`9` 多 15 筆。
  - **新增驗收 A17：變體區規模上界**。對全部 2,357 個真實 token 當查詢實跑，斷言無任何查詢的變體區 > 100 筆，且 p99 ≤ 12。
    這條堵死「規則放寬後沒人發現該區已不可用」——**它是唯一一條在驗規模而非驗正確性的驗收**。

> 這條與 Codex 1.2 的第二種解法（「若堅持 42，則須明確撤回變體字首」）殊途同歸，
> 但 Codex 是從「42 與 43 對不起來」推出來的，主持人是從「該區會不會不可用」推出來的。**兩條路都指向撤回字首。**

## 逐項判定

### 1. 需求與邊界缺漏

| # | 項目 | 嚴重度 | 判定 | 理由 |
|---|---|---|---|---|
| 1.1 | 多 token 的「全中」單位未定義 | Blocker | **接受** | 屬實且是最嚴重的一條。v0.1 只寫「變體全中」，確實允許 token A 靠倒讀、token B 靠字形拼成一次全中——那正是 N15 禁止的組合變體，被自己的規則從後門放進來。修法：兩條規則是**各自獨立的 predicate，每條必須單獨覆蓋全部查詢 token**；任一 token `flip()` 為 `null` 則整條倒讀 predicate 為 false。已實跑驗證：查詢 `M 40` 在此規則下變體區為 **0**（`flip('40')` 因 `4` 表外回 `null`），若改成逐 token OR 會誤放行 |
| 1.2 | `SH/HS` 歸屬與數量矛盾 | Blocker | **接受** | 屬實。**主持人在 Codex 回報前已獨立自查到同一條**（見上方事實查核）。根因是把 handoff 的**記錄端**量測直接當成**查詢端**語意——本 repo 第四次犯「從已聚合產物回推語意」。Codex 給的兩條解法中採第二條（撤回變體字首），與 S1 的結論一致。修正後實測：查詢 `SH` 主區 **37**、變體區 **42**（全部倒讀理由）|
| 1.3 | `canon` 代表字查詢與 A15(e) 衝突 | Blocker | **部分接受** | **問題屬實**：A15(e) 寫「查詢 `0`／`12` 不得因壓平而重複計入」，若讀成「不得產生任何 variant」，會讓 `0/O` 等價類變成單向，語意破裂。**但 Codex 的修法不必要**：它建議加一條「原樣已命中的同一記錄不得重複進 variant」——這在 **D31（變體只在 imprint 為 MISMATCH 時計算）下自動成立**，原樣命中的記錄根本不會進入變體計算路徑。多寫一條規則會產生兩個真理來源。**正確作法**：A15(e) 改成雙向對稱斷言（查詢 `0` 須能接住記錄 `O`、反之亦然），並在 D31 明寫「原樣不重複進變體是本規則的推論，不另立規則」。數字改用實跑值：撤回字首後查詢 `0` 變體 **0 筆**（單字元不做字形）、`12` 變體 **4 筆** |
| 1.4 | 倒讀轉換方向只藏在 B22 | High | **接受** | 屬實。D32 從未明說 `flip` 作用在查詢端還是記錄端，兩種實作在字首級下產生不同集合。撤回字首後兩者在完全級因對合而等價，**但仍必須明寫**——語意不該靠「碰巧等價」成立。修法：D32 明定「只轉換查詢 token，再與原始記錄 token 比對」 |
| 1.5 | 變體理由的輸出契約未定義 | High | **接受** | 屬實且是實作最容易做錯的一條。理由若寫回 indexed item，連續搜尋會留下上一個查詢的 stale reason——`app.js` 有 120 ms debounce，快速輸入時連續搜尋是常態。修法：理由為 **query-scoped 結果 metadata**，同一 ID 至多一筆，理由集合為 `{flip}`／`{canon}`／`{flip,canon}`，**不得寫回 `_tok`／`_tokCanon` 所在的 item** |
| 1.6 | 「原樣失敗」是逐記錄還是整次查詢 | Medium | **接受** | 屬實。弱實作可能只在 `mainCount===0` 時才整批啟用變體，仍符合「原樣比對失敗時」的一種讀法。實測 `SH`（主 37／變 42）與 `01`（主 162／變 73）都是主區與變體區同時非空的真實案例，可直接當具名驗收 |
| 1.7 | 零／單／多 token 未成真值表 | Medium | **接受** | 屬實。併入 Codex 4.3 的單一 admission truth table |
| 1.8 | 其他條件 mismatch 須壓過 variant | Medium | **接受** | 屬實。A14 把顏色形狀都設成 match，正好避開這個風險——這是取樣偏誤 |
| 1.9 | 「無新的失敗路徑」陳述過度 | Low | **接受** | 屬實。改為「無新增 I/O／網路失敗路徑；新增的是語意與結果契約失敗，由 A／B／E／F 組驗證」 |
| 1.10 | 缺少可觀察的效能門檻 `[新增需求]` | Medium | **拒絕—範圍蔓延** | Codex 自己標了 `[新增需求]`。既有 6,295 筆線性掃描早已在 120 ms debounce 下運作，本次只在 imprint 為 MISMATCH 時多算 2 個 predicate（實測全量掃描仍在毫秒級）。**效能門檻若要設，是既有規格的事，不是本次增補的事**。不做的可觀察後果 Codex 沒說出具體到可裁決的程度。移入「後續版本」 |

## 修訂後的規則（供 v0.2 使用，全部經實跑驗證）

**Admission truth table（唯一語意來源）**

| imprint 原樣狀態 | 是否計算變體 | 結果 |
|---|---|---|
| `OFF`（輸入為空）| 否 | 條件未啟用 |
| `NO_TOKEN`（有輸入但 0 token）| 否 | 不套用 imprint 篩選 |
| `MATCH` | 否 | 主區（tiers 0/1/2）|
| `PARTIAL` | 否 | 部分符合區 |
| `UNKNOWN` | 否 | 未提供區 |
| `MISMATCH` | **是** | 見下 |

變體計算（僅 `MISMATCH` 時）：兩條**獨立** predicate，各自必須**單獨覆蓋全部查詢 token**，且**只接受 token 完全相等**：

- **倒讀**：任一查詢 token 的 `flip()` 為 `null` → 整條 false；全部為 fixed point → 整條 false（不算變體）
- **字形**：任一查詢 token 長度為 1 → 整條 false；否則雙邊 `canon` 後比對
- 任一 predicate 為 true → `Cond.VARIANT`，理由為 true 的那些；兩條皆 true → 雙理由
- 皆 false → 維持 `Cond.MISMATCH`（排除）

**分區優先序**：`mismatch > variant > unknown > partial > main`

| 查詢 | 主區 | 部分 | 未提供 | 變體 | 倒讀／字形／雙 | 這個案例守著什麼 |
|---|---|---|---|---|---|---|

| `HS` | 44 | 0 | 2085 | 4 | 3／1／0 | 反向不對稱 |
| `01` | 162 | 0 | 2085 | **73** | 71／1／**1** | **唯一自然出現的雙理由案例**（A15f）|

## 結論
