## 0. 一句話

讓使用者依**藥品外觀特徵**（刻字、顏色、形狀、刻痕）縮小 TFDA 6,295 筆藥品的候選清單，
供**人工比對確認**。這是「外觀條件檢索 → 候選藥物 → 人工確認」，
**不是**「輸入照片 → 系統宣稱這就是某藥」。

---

## 1. 目標

1. 由 TFDA 官方 Open Data 建立可搜尋的藥品外觀資料集（全量 6,295 筆）。
2. 支援 imprint（藥錠刻字）、顏色、形狀、刻痕的組合搜尋（條件間 AND）。
3. 支援中文品名／英文品名／許可證字號的部分字串搜尋。
4. 顯示官方藥品外觀圖片與 TFDA 原始外觀欄位。
5. 手機單手可操作（藥袋／藥車／病房／藥局現場為主要使用情境）。
6. 資料由 GitHub Actions 定期更新；更新失敗不得破壞既有可用資料。

### 3.3 標註（imprint）的髒值

- 標註一 3 種含中文的值：`六邊形裡面有K`、`頭CL;;;CL`、`無`（字面「無」3 筆）
- 標註二 2 種：`無`（**6 筆**）、`尾016;;;016`
- 字面「無」＝ **9 個欄位出現、6 筆記錄**（3 筆兩欄皆為「無」）。
  其中 **3 筆同一記錄的另一欄仍有有效 token**（`GL14 5`／`GBL 4`／`GBL`）。
  **欄位出現次數 ≠ 記錄數**——這條在 v1.2 曾被寫成「9 筆」，由 oracle 自檢擋下
- `頭CL;;;CL` 與 `尾016;;;016` 屬**同一筆記錄**（全資料集僅此一筆使用頭／尾字樣）
- **41 筆標註一 === 標註二**；**68 筆只有標註二、沒有標註一**
- 標註一 47 筆、標註二 13 筆含 `;;;` 多值
- **兩欄清理後皆無有效 token 的記錄：2,085 筆**（非 2,150；2,150 只是標註一為空的數量）

### 3.4 判別力實測

色＋形＋刻痕的 415 種**組合**中，>100 筆的組合有 12 種、涵蓋 3,080 筆藥品（49%）。
（此處是「組合分布」，用於理解判別力上限，**不得**用來推導驗收筆數——見 §3.2 的警告。）

**結論：imprint 是唯一有效鑑別器，而 2,085 筆（33%）完全沒有可搜尋的刻字。**
近半數情況下使用者「沒有更多條件可補」，UX 必須誠實面對（§8.4）。

## 5. 架構決策

### D1 缺值不排除，分區顯示

勾「白色」時，顏色無法判定的記錄**不進主區**，但另闢摺疊區
「因資料未提供而無法排除（N 項）」。計數文案：「符合條件 N 項（另有 M 項資料未提供）」。

**為什麼不選「純 AND 排除」**：手上那顆藥可能正是 TFDA 沒填顏色的那筆。
靜默排除會讓使用者以為已窮盡候選——這是本工具**唯一會造成臨床傷害**的失效模式。

**為什麼不選「預設排除 + 勾選開關」**：預設值仍是漏檢，臨床現場不會有人去點那個開關。

### D1.1 三值真值表（**搜尋核心的唯一語意定義**）

**兩階段求值，順序不可對調：**

**階段 ①　條件是否啟用** —— 未啟用的條件一律 `match`，**且不查看記錄的任何值**。
未啟用的定義：顏色／形狀未勾選任何 chip；刻痕為「不限」；imprint 或名稱輸入框
`trim()` 後為空字串。

> 這一階段是 v1.2 新增的。v1.1 把「條件未啟用」與「記錄缺值」寫在同一張表的不同欄位，
> 兩者在「沒勾任何顏色 ＋ 該筆顏色也是空的」這格**同時成立**，
> 兩種合法解讀會產生完全不同的初始畫面與未提供區。

**階段 ②　已啟用的條件才判三值**：

| 條件 | `match` | `mismatch` | `unknown` |
|---|---|---|---|
| 顏色（已勾選集合 S） | 記錄顏色**任一值** ∈ S | 記錄顏色非空且無任一值 ∈ S | 記錄顏色拆解後為空 |
| 形狀（已勾選集合 S） | 同上 | 同上 | 同上 |
| 刻痕（已選 v ≠ 不限） | 記錄刻痕任一值 = v | 記錄刻痕非空且無值 = v | 記錄刻痕拆解後為空 |
| imprint（有效查詢，見 D3） | **每個** Q token 皆在記錄 token 集合中命中 | 記錄 token 集合非空且至少一個 Q token 無命中 | 記錄 token 集合為空 |
| 名稱（查詢 Q） | `toUpperCase(Q)` 為 `toUpperCase(zh)`／`toUpperCase(en)`／`id` **任一**的子字串 | 其餘 | **不存在**（`en` 與 `id` 恆非空，恆可判定） |

> 名稱比較一律先 `toUpperCase()` 再比子字串（中文與許可證字號不受影響，無大小寫）。
> 這是 A9 要求「小寫 `sodium` 命中」的唯一依據，不得用個案特判達成。

**分區規則（三選一，互斥且窮盡）：**

1. 任一條件為 `mismatch` → **排除**（不出現在任何區）
2. 否則若任一條件為 `unknown` → **未提供區**
3. 否則（全部 `match`） → **主區**，並依 D3 的 imprint 等級再分三個子區

**組間 AND、組內 OR。** 顏色與形狀可複選（組內 OR），刻痕單選，各組之間 AND。

> 複選採 OR 的理由：粉／紅／橘、藍／藍綠在實體藥錠上高度混淆，
> 強迫單選等於要求使用者先做一個他做不到的判斷，違反 D1 確立的漏檢優先。

### D2 本專案自建全量 canonical；quiz 這輪不動

（同 v1.0，未變更。）不選「先抽共用層」：quiz 卡在 V5 批次 4（PR #15 待 merge、599 測試）。
不選「圖片跨 repo 引用」：資產鍵是識別碼定址而非內容定址，TFDA 原地換圖時兩邊會靜默不一致。
已知代價：短期重複約 150 行程式碼與約 50 MB 圖片。

### D3 imprint = token AND + 三級**互斥**分區

**token 生成（逐欄）**：對標註一、標註二**各自**：拆 `;;;` → 大寫化 →
非 `[A-Z0-9]` 字元一律轉為分隔 → 切 token → 去空。
字面「無」因此自然產生零 token，**不需要特判**。
**記錄的 token 集合 = 兩欄 token 的聯集**（去重）。

**查詢的三種狀態（唯一定義，不得由空集合量詞自行推導）**：

| 狀態 | 條件 | 行為 |
|---|---|---|
| **未啟用** | 輸入框 `trim()` 後為空 | 條件為 `match`（D1.1 階段 ①） |
| **有效查詢** | 非空且產生 ≥1 個 token | 依 D1.1 階段 ② 判三值 |
| **無有效 token** | 非空但產生 **0** 個 token（例如 `無`、純中文、純符號） | **不套用 imprint 篩選**，並在搜尋列下方顯示：「輸入內容不含可搜尋的英數字元，已忽略此條件」 |

> 第三狀態是 v1.2 補上的。v1.1 只寫「每個查詢 token 皆命中」，
> 零 token 時量詞在空集合上**真空成立**，會讓所有有 token 的記錄都 match——
> 而規格另一處（A8）又要求搜尋 `無` 不命中任何記錄，兩者不可能同時實作。
> 選「忽略並提示」而非「回 0 筆」的理由：回 0 筆會讓使用者以為查無此藥（最高風險）；
> 靜默全通過則是隱瞞。提示讓使用者知道發生了什麼並自行改輸入。

**比對**：每個查詢 token 都必須在**聯集**中命中（AND，不計順序）。
單一 token 的命中分三級：**完全相等 > 字首 > 包含**。
記錄的等級 = 所有查詢 token 中**最差**的那一級。

**三級為互斥分區**（一筆記錄只出現在一區），UI 各區加標題與筆數：
「完全符合（N）」「字首符合（N）」「包含（N）」。

> v1.0 曾在 A3 誤用累計口徑（`T` 寫成 95／428／950）。**全文統一為互斥**：
> `T` 是 95／333／522，`10` 是 72／129／67。

**為什麼 token 取兩欄聯集而非要求同欄全中**：使用者看著一顆藥讀出所有看得到的字，
不會知道哪一段屬於 TFDA 的「標註一」。要求同欄全中會製造漏檢。

**為什麼不選純子字串**：`T` → 950 筆、`1` → 1148 筆，且 `M 40` 順序敏感。
**為什麼不選只做完全比對**：使用者只看得出刻字的一部分正是典型情境。

規則寫死在 `search.js`，**無分數、無門檻、無 AI confidence**。

### D4 排序

主區內：① imprint 完全符合 ② 字首符合 ③ 包含
（未輸入 imprint 時全部視為同一級）。
**各分區內的 tie-breaker：中文品名 `localeCompare('zh-Hant')` → 許可證字號**（穩定、確定性）。
未提供區同樣依此 tie-breaker 排序。

刪除 v1.0 的「多欄位符合」層：條件間是 AND，該層恆空。

### D5 chips 即 TFDA 受控詞彙，1:1，不建 mapping

- 顏色 chips = 13 種實測值（**補上「透明」「藍綠」；刪除不存在的「其他」**），**複選**
- 形狀 chips = 13 種實測值（**補上五／六／八邊形、水滴形、雙圓形、液劑、顆粒散劑；
  刪除不存在的「長圓形」「多邊形」**；「其他」在形狀中確實存在故保留），**複選**
- 刻痕 = **不限／無／直線／十字**，**單選**

保留 raw value 原樣供顯示與 audit；不做 raw→normalized 轉換。防線是 D6。

### D6 詞彙快照鎖（`data/vocab.lock.json`）

管線比對來源實際出現的顏色／形狀／刻痕值集合與快照檔，
**出現快照外的新值即中止發布**，要求人工更新快照並同步 UI chips。

**並且：UI chips 的可選值集合必須與 `vocab.lock` 的對應集合完全相等**（集合相等，
非數量相等），由靜態契約守著。否則管線放行了新值、UI 卻沒有 chip 可以選到它，
那些藥從此在條件搜尋中不可見且無人察覺。

### D7 標註一/二 不得標為「正面／背面」

實測 41 筆兩欄完全相同、68 筆只有標註二、僅 1 筆記錄用「頭CL」「尾016」表達面向。
TFDA 未定義兩欄的面向語意。卡片與詳細頁一律標「標註一」「標註二」。→ N9。

### D8 特殊劑型／特殊氣味

兩欄 100% 空。**不輸出到前端 JSON**（否則是兩欄永遠為空的 payload 與兩行永遠的
「資料未提供」）；**由管線監測**：若由全空轉為有值，輸出**警告但不中止**，
警告須含**欄位名、非空筆數、代表 id 與代表值**。是否納入 UI 由人工另行裁決。

### D9 發布守門

- 來源筆數 **< 5,000** → 中止（下限守門，與下方變動幅度守門**彼此獨立**）
- 必要欄位缺漏 → 中止
- 相對前版變動幅度 > ±3%，或單次移除 > 50 筆 → 中止（`--allow-any-delta` 人工放行）
- 許可證字號唯一性斷言，違反即中止
- 資產鍵碰撞 → 中止
- 詞彙快照外的新值 → 中止
- **全有全無**：任一驗證失敗則 `data/` 的**已發布內容**完全不更新
- **下載限制**：來源與圖片皆設連線／讀取 timeout、限制 redirect 次數、
  設回應大小上限；逾時或超限視同失敗，走既有重試與中止路徑
- **併發**：workflow 以 `concurrency` 群組限制同一 branch 僅一個資料更新在跑，
  後到者取消（不自建 lock 檔）

### D12 兩個層次：資料就緒切換點（rename）與對外發布快照（commit）

v1.0 的順序是「先發布 `appearance.json` → 再抓圖」，中間存在
「JSON 已宣告新圖檔名、圖檔尚未存在」的視窗。修正為：

```
寫 data/appearance.json.staging  →  抓圖（寫入 data/img/）
   →  回填雜湊到 staging  →  verify  →  rename（資料就緒切換點）
   →  commit（唯一對外發布快照，一次帶入 JSON 與圖片）
```

- **rename ＝ 資料就緒切換點**（工作目錄內）；**commit ＝ 唯一對外發布快照**。
  **rename 後、commit 前的任何失敗都不得 commit。**
  v1.1 把 rename 稱為「唯一發布點」是不精確的——對使用者而言，
  真正可見的版本切換發生在 commit／deployment。
- `carryHashes()` 仍從**已發布**的 `data/appearance.json` 讀前版雜湊
  （不使用 `$RUNNER_TEMP` staging，否則前版讀不到 → 全量重抓，即姊妹專案的 SC-3 回歸）
- **不對 `data/img/` 做暫存區與目錄原子交換**（N13、L10）。

#### D12.1 provenance 不變量（**取代 v1.1 的過強宣稱**）

v1.1 曾寫「資產鍵由許可證字號衍生，跨藥錯圖在建構上不可能發生」。
**這個宣稱是錯的**：資產鍵只證明**命名空間**，不證明**內容來源**。
若下載器把記錄 A 的 key 配上記錄 B 的 `src`（索引錯位），
檔名斷言照樣全過，而畫面上是 A 的品名配 B 的照片——正是威脅模型第 3 項。

因此改以三條**同時成立**的不變量防守（由 C12 實跑守著）：

1. **命名空間**：`data/img/<key>-<n>.webp` 的 `<key>` === `sha1(該筆 id)[:16]`
2. **來源歸屬**：`imgs[n].src` 必須出自**同一 id 的來源列**「外觀圖檔連結」欄，
   且 `n` 的順序與數量與來源列的 `;;;` 拆解結果逐項對帳
3. **內容一致**：落地檔案的實算 sha256 === `imgs[n].sha256`

三者缺一不可。只驗第 1 條等於沒驗 provenance。

### D10 圖片鏡像與 cache key

長邊 640、WebP q78，下載 → Pillow 完整解碼 → 轉檔 → sha256。
資產鍵 `sha1(許可證字號)[:16]-<序號>.webp`。
**零位元組回應必須視為失敗**（來源對不存在的圖回 200 + 0 bytes）。

**不外連的理由**：實測中位 1.5MB、單頁 20 張約 68 MB、無有效快取標頭、無縮圖參數。
原始需求「第一版不要自建圖片 database」的免責條款已由實測觸發。

#### D10.1 內容版本 cache key（v1.2 新增）

檔名固定為 `sha1(id)-n.webp`，**TFDA 原地換圖後我方檔案內容變、URL 不變**，
已快取的瀏覽器會繼續顯示舊圖（L11）——這就是威脅模型第 3 項，v1.1 完全沒防。

**修法**：前端請求時附內容版本：`img/<key>-<n>.webp?v=<sha256 前 8 碼>`。
`sha256` 已在 `imgs[n]` 中，前端直接取用。內容一變 cache key 就變。

**為什麼不把 sha 嵌進檔名**：那會在每次換圖時留下孤兒檔，需要額外的清理邏輯與
「哪些孤兒可刪」的判斷，並破壞資產鍵不變量與續傳判定。`?v=` 兩者都不動。

### D14 圖片內容新鮮度：季度 HEAD 掃描 ＋ 抽樣深驗 ＋ 永久壞圖的人工例外

**問題**：來源無 ETag／Last-Modified，URL 未變不代表內容未變。
一般排程的增量判定（新增／URL 變更／檔案不存在／雜湊不合法）**偵測不到原地換圖**。

**v1.4 修訂（實測後推翻 v1.3 的作法）**：原本規定季度 `--verify-all` 全量重抓，
分四批、**22 GB × 4 = 88 GB/年**。三項實測改變了結論：

| 實測 | 結果 |
|---|---|
| 姊妹專案 2026-08-04 記錄的原圖 sha256，抽 30 張重抓 | **位元組 30/30 完全相同**（8 天窗口、n=30，證據弱但方向一致）|
| 圖檔 URL 結構 | UUID-keyed（`shapeImg/<uuid>[_img_N]`）→ **換圖較可能換 UUID**，那由一般模式的增量判定就抓得到 |
| **HEAD 請求** | **可用，且 `Content-Length` 準確**（3/3 與 GET 位元組數一致）|
| Range 請求 | **不支援**（回 200 全檔），沒有「只抓片段做指紋」這條路 |

**處置**：

1. **季度新鮮度檢查 `--freshness`，兩層，不下載全量**：
   - ① **HEAD 掃全量 6,798 張**，比對 `Content-Length` 與 manifest 的 `src_bytes`（幾 MB）
   - ② **隨機抽樣深驗**（預設 100 張，約 366 MB）：真的 GET 下來重新轉檔比對 `sha256`，
     兜住「長度剛好不變的改寫」——那是 ① 唯一漏得掉的情形
   - **問不出長度 ≠ 沒變**：HEAD 失敗或缺 `Content-Length` 一律列為需人工確認。
     把問不出來當成沒變，等於讓壞掉的端點自動過關，而那正是這道檢查要抓的東西
   - **不寫入任何檔案、不自動更新圖片**：官方換圖可能代表藥品外觀真的變了，需要人看過
   - 季度流量由 88 GB/年 降到約 **1.5 GB/年**
2. **`--verify-all` 保留給人工全量稽核，不再排程。**
3. **永久壞圖例外清單** `data/image-exceptions.json`：
   人工審核後可標記特定圖片為「官方暫無可用圖片」。
   - **鍵為 `id + src`（逐圖，不是逐記錄）**。多圖記錄的單一壞 URL
     **不得**連帶遮掉同筆其餘有效官方圖；只有該筆所有來源圖都無法使用時 `imgs` 才為空
   - 欄位：`id`、`src`、判定日期、理由
   - **不得由暫時性網路失敗自動加入**（管線不得寫入此檔）
4. **例外的恢復處置**：新鮮度檢查**仍須探測例外清單中的 URL**。
   若已恢復為可解碼圖片 → **警告並列入人工裁決報告**（與 D8 一致），
   在人工撤銷例外前該圖維持 placeholder。
   **不採「恢復即中止 workflow」**——圖片恢復是好事，用中止懲罰它會讓人
   傾向乾脆不清理例外清單。

**已知殘餘風險**：長度剛好不變的改寫，若未被抽樣抽中就會漏。
抽樣 100/6,798 對「一批同型變更」的偵測力高（k=100 張受影響時約 95%），
對「單張孤立改寫」低（k=1 時約 1.5%）。這是刻意的取捨：
單張孤立改寫的後果是一顆藥顯示舊照片，與 88 GB/年的成本不相稱。

### D11 前端架構

- 全量 `appearance.json` 一次載入，記憶體內線性掃描
- **搜尋用 token 於載入時由 `search.js` 現算**，不持久化在 JSON（見 D15）
- 輸入 debounce 120 ms；首屏渲染 24 張卡片，捲動載入更多（`IntersectionObserver`）
- 圖片 `loading="lazy"` + `decoding="async"`
- 每次條件變動即時更新候選數（不需按「搜尋」）

### D13 驗收數字綁定凍結 baseline

§10 的所有精確筆數綁定 **`tests/baseline-2026-08-12.json`**（來源全量快照）。
**週更的 live 資料只驗不變量與守門，不驗精確筆數。**

沒有這條，第一次合法的 TFDA 更新就會讓一整組驗收紅燈，
接著養成「紅了就改常數」的習慣，回歸價值歸零。

**外部錨點**：快照自身內含的 hash 不足以證明凍結（快照與其 hash 可一起被改）。
因此把來源 ZIP 與 `42_5.json` 的 sha256 **寫在本文件開頭**——
竄改快照必須同時修改規格文件，不再是一個檔案內的自我證明。

**expected ID sets 的產生方式**（A 組依據）：
- 須標明**建立日期、對應資料 hash、獨立產生方式、人工核准者**
- **不得由受測函式（`search.js`）在測試時生成或更新**
- 測試碼中**不得存在任何回寫／更新 expected 的路徑**（含 `--update-snapshot` 類旗標）
- 全部精確數字只引用**同一份已審核的 expected manifest**，不另抄常數來源
  （避免 baseline／A 組常數／20 筆 fixtures 形成三套真相）

### D15 canonical JSON 不持久化「搜尋衍生」欄位

不持久化 `mtok`／`ntok` 等**搜尋**衍生欄位。理由：
（a）衍生欄與 raw 必然漂移，而漂移的後果是「管線與前端對同一筆藥的 token 不同」；
（b）6,295 筆的 token 化在載入時是毫秒級；
（c）沿用「正規化只有一份」的紀律——現算保證只有一份。

**允許保留的衍生欄（完整性／manifest 用途，不得因本條被刪）**：
`meta.content_hash`、`meta.count`、`meta.vocab`、`meta.images_bytes`、`imgs[].sha256`。
v1.1 的標題寫成「只存來源／顯示欄位」會讓人誤刪這些，故更名。

### D17 第四分區「部分符合」（v1.3 新增，來自 A12 的雙向反例）

**問題**（A12 的 false negative，實跑證實）：查詢 token 對記錄 token 取 AND，
只要一個查詢 token 沒中就判 mismatch，該筆**被完全排除**，連未提供區都進不去。
而 TFDA 的標註欄常只記錄部分刻字——**1,293 筆（有 token 記錄的 30.7%）只有單一 token**。
使用者照著藥錠把看到的字全部讀出來，反而把記錄不完整的那批藥全部濾掉：
**輸入越完整、漏檢越嚴重**。這與 D1 確立的漏檢優先直接衝突，
而缺值有未提供區接住、部分記錄沒有。

**處置**：imprint 條件新增第四種結果 `partial` ——
「至少一個查詢 token 命中、但非全部命中」。

- **「一個都沒中」仍然是 mismatch**：使用者讀到的字在那顆藥上完全不存在，
  排除它不是漏檢。「部分符合」不是「什麼都收」。
- **分區優先序：mismatch > unknown > partial > main。**
  unknown 排在 partial 前面的理由：兩者都是「無法排除」，但 unknown 是
  「TFDA 這個欄位根本沒填」，partial 是「填了、只是不完整」，前者不確定性更大。
- UI 標題：「部分符合（N）—— TFDA 只記錄了部分刻字，無法排除」，排在「包含」之後。
- **單 token 查詢的部分符合區恆為 0**（全中或全不中，沒有中間態）——由 C16 守著。

**不改變任何既有數字**：A1／A3／A6b 的三級與未提供區完全不變（已實跑驗證）。
唯一變化是原本被排除的記錄改列第四區，例如 `M 40` 多出 **504** 筆。

### D18 單字元查詢 token 不啟用「包含」級（v1.3 新增，來自 A12 的雙向反例）

**問題**（A12 的 false positive，實跑證實）：查詢 `S` 的包含級有 **423 筆**，
內容是 `YSP`、`EVEREST`、`ASTAR` 這類完全不像 S 的刻字。
單字元的「包含」實質上是「這顆藥的刻字裡有這個字母」，
與使用者看到的「藥上只印了一個 S」是兩件事。即使已分區揭露，
423 筆的第三區在藥車前不可用。

**處置**：查詢 token 長度 = 1 時，只保留**完全**與**字首**兩級。

**這是刻意接受的漏檢**：若藥錠真的只看得出一個字母、而 TFDA 記的是長字串，
該筆會被排除，且單 token 查詢沒有 D17 的部分符合態可接住。
取捨理由：留著等於用不可用的清單換一個理論上的涵蓋率。

**受影響的凍結數字（依 D13 政策，規格與 oracle 同步更新）**：

| 案例 | D18 前 | D18 後 |
|---|---|---|
| imprint `T` | 95／333／522 | **95／333／0** |
| imprint `S` | 174／657／423 | **174／657／0** |
| imprint `M 40`（M 為單字元） | 2／4／13、部分 504 | **2／4／5、部分 294** |
| 白+圓形+無+`S` | 16／78／35 | **16／78／0** |
| imprint `10`（token 皆 ≥2 字元） | 72／129／67 | 不變 |

### D16 前端資料載入必須 fail-closed（任何資料契約違反）

下列任一情形皆視為載入失敗，顯示**「資料暫時無法載入，請稍後再試」**並**停用搜尋介面**：

- 取檔層：404／其他非 200／逾時／JSON 解析失敗
- 結構層：`meta.schema` 不符、`items` 非陣列、`items` 為空
- **逐筆契約層**：缺 `id`、`id` 重複、欄位型別錯誤（如 `color` 非陣列）、
  `imgs` 結構損壞（元素缺 `file`／`src`／`sha256`）

**絕不可**表述為「找不到符合的藥品」或顯示 0 筆結果——
部署或網路錯誤會被使用者讀成「這顆藥不在資料庫裡」，直接命中最高風險。

> v1.1 只列了取檔層與結構層。若 `items` 非空但個別記錄損壞，
> 資料仍會進入搜尋並產生**部分結果**——那是最危險的一種：畫面看起來正常。

```
TFDA opendata 42 (ZIP)
   │  ① tools/fetch-appearance.mjs（Actions 端；前端不得直接 fetch → L3）
   │     timeout／redirect 上限／大小上限逾越 → 中止

   ├─ ZIP 內無／有多個符合 schema 的 JSON      → 中止

   ├─ 必要欄位缺漏                             → 中止
```

## 7. 資料模型（`data/appearance.json`）

```
meta: {
  schema: 1,
  source: "TFDA 藥品外觀資料集 (opendata 42)",
  source_file: "42_5.json",
  source_version: "YYYY-MM-DD",   // ZIP entry 的 DOS date，非執行時間（冪等）
  source_rows: 6295,
  content_hash: "sha256:…",       // **下載回來的 ZIP 原始位元組的 sha256**，
                                  // 與產物格式無關，格式微調不會造成假變更
  count: 6295,
  vocab: { color: [...], shape: [...], score_mark: [...] },   // 本次實際出現的值
  images_bytes: 91239644          // null＝未計；正整數＝已鏡像資產總量。
                                  // **0 不是合法值**（D38，見該節）
}

items[]: {
  id:    "衛部藥製字第061870號",   // 許可證字號（唯一鍵）
  zh:    "尼肺纖達軟膠囊150毫克",
  en:    "Nifibro soft capsule 150 mg",
  color: ["棕"],          // raw，保留順序與重複（膠囊兩截可能是 ["白","白"]）
  shape: ["橢圓形"],
  score_mark: ["無"],     // 刻痕。刻意不叫 score，避免與禁止的評分混淆
  size:  ["18.5"],        // raw，多值原樣保留，不臆測長寬
  mark1: "NT 150",        // **raw，原樣保留**。字面「無」照樣保留並照樣顯示
  mark2: null,            //   （TFDA 就是這樣寫，顯示它是誠實的）
  imgs: [                 // **每張圖一個具名記錄**，不用平行陣列
    { file: "img/3f2a…-0.webp",
      src:  "https://mcp.fda.gov.tw/…",
      sha256: "…",        // **轉檔後 WebP** 的雜湊：D12.1 第三條 ＋ 前端 ?v= cache key
      src_bytes: 301106 } // **原圖** 的 Content-Length：D14 HEAD 掃描的唯一基準
  ]                       // 前端請求時附 ?v=sha256.slice(0,8)（D10.1）
}
```

- `imgs` 的三條 provenance 不變量見 **D12.1**（命名空間／來源歸屬／內容一致）
- **不含** `mtok`／`ntok`（D15：載入時現算）
- **不含** 特殊劑型／特殊氣味（D8：管線監測，不進前端）
- `imgs` 為空陣列 = 該筆無官方圖或在例外清單中 → UI 顯示 placeholder
- **缺值一律為 `null` 或空陣列**，不得填入 `"未知"`、`"-"` 等佔位字串。
  唯一例外是 `mark1`／`mark2` 的字面「無」——那是 TFDA 的原值，原樣保留；
  它**不會**產生任何搜尋 token（D3 的逐欄清理自然達成）

## 8. UI 規格

### 8.1 首頁（mobile-first）

標題「藥丸偵探 Pill Detective TW」，副標「台灣藥品外觀搜尋 — …」（v1.5 更名）；自由文字框「藥品上看到什麼文字或數字？」；
顏色 13 chips（複選）；形狀 13 chips（複選）；刻痕 不限／無／直線／十字（單選）；
即時計數「符合條件 N 項（另有 M 項資料未提供）」；
另有「已知藥名？中文／英文／許可證字號」欄。

touch target ≥ 44 × 44 px；**只有搜尋列 sticky，條件面板隨頁捲動**（v1.5，見 D19）；卡片圖片在 375 px 寬下不得小於 96 px 見方。
風格 clinical／clean／calm；不做漸層、glassmorphism、hero banner、統計卡、
首頁教學長文、無臨床意義動畫。

**字型**：自架或使用系統字級，**不從第三方 CDN 載入字型**——
否則每次開啟都會把使用者 IP 送給第三方，與 §9 的隱私主張互相矛盾。

### 8.2 結果卡片

官方外觀圖片｜中文品名｜英文品名｜許可證字號｜外觀（白｜圓形｜無刻痕）｜
標註（標註一：ABC　標註二：10）｜尺寸｜「查看詳細資料」

### 8.3 詳細（modal）

圖片（多圖可切換）、中文品名、英文品名、許可證字號、形狀、顏色、刻痕、
外觀尺寸、標註一、標註二。缺值顯示「資料未提供」。
固定標示「資料來源：衛生福利部食品藥物管理署 Open Data」＋ 資料集頁連結。

### 8.4 結果數量的 UX

| 情境 | 行為 |
|---|---|
| 資料載入失敗 | 「資料暫時無法載入，請稍後再試」，停用搜尋（D16）。**不得**顯示 0 筆 |
| imprint 輸入非空但無有效 token | 顯示「輸入內容不含可搜尋的英數字元，已忽略此條件」，其餘條件照常套用（D3） |
| 主區 0、未提供區 0 | 「找不到符合的藥品」＋ 放寬建議（依序：刻痕 → 形狀 → 顏色），**不得自動修改條件** |
| 主區 0、未提供區 > 0 | **不得**說「找不到」；直接展開未提供區並說明「TFDA 未提供該欄位資料，無法排除」 |
| 1–20 | 直接顯示 |
| > 20 且尚有條件未填 | 「候選藥品較多，建議加入藥錠文字、顏色或形狀」 |
| > 20 且所有條件皆已填 | **改為**「已無更多條件可縮小，請以圖片人工比對」——不得繼續催促補條件 |

> **「所有條件皆已填」僅指四個外觀條件**：imprint、顏色、形狀、刻痕。
> 名稱欄**不納入**此判定——它不是縮小外觀候選的手段，
> 使用者若已知藥名就不需要這個工具。

### 8.5 臨床安全文案（固定顯示，不可摺疊）

> 本工具依 TFDA 公開藥品外觀資料提供候選結果，外觀相似不代表為同一藥品。
> 實際藥品仍應依原包裝、藥袋、許可證資訊或由醫療專業人員確認。

**全站禁止出現身份宣稱片語**（以片語為單位，非單詞）：
「辨識成功」「就是這顆」「確認為」「本品為」等。一律用「可能符合的藥品」「候選藥品」。

## 14. 修訂紀錄

### v1.10 → v1.11（`images_bytes` 的 sentinel 拆解，2026-08-15）

#### D38 `images_bytes`：0 不是合法值

**怎麼發現的**：2026-08-15 首次手動觸發週更（在此之前 `update-data.yml` 從未執行過，
只有 2026-08-12 那次一次性 `bootstrap-images`）。管線全綠、137 測試全過、資料照常發布，
但 `appearance.json` 比前一版少 7 bytes——`content_hash` 與 6,295 筆全部相同，
差異只在 `meta.images_bytes`：**91,239,644 → 0**，而 `images_complete` 仍是 `true`。

**成因**：`fetch-images.py` 的 `if not todo: return 0` 早退在 `images_bytes` 重算與
manifest 回寫**之前**。而「待處理 0 張」正是週更穩定後每一週的常態，不是例外路徑。

**真正的缺陷不是數字錯，是 0 同時代表兩個相反狀態**：

| `images_bytes: 0` 的意思 | 來源 |
|---|---|
| metadata-only 發布，圖片根本還沒上 | D23，C10c 正是斷言這個 |
| 圖片 6,798 張全部就緒，只是收尾沒跑完 | 這次的 bug |

C10c 因此是一條**弱驗收**：它斷言的值不再唯一對應它宣稱的狀態。
這與「欄位出現次數 ≠ 記錄數」是同一類錯——**一個值被迫兼職兩種語意**。

**決策（三條一起，缺一條就只剩約定在守）**：

1. **語意**：`null`＝未計，正整數＝已鏡像資產總量，**0 不再是任何合法狀態**。
   staging 初建與 metadata-only 發布都寫 `null`（原為 `0`）
2. **`fetch-images` 待處理 0 張時不得早退**：空的 `todo` 讓下載段自然成為 no-op，收尾照跑
3. **`--publish` 獨立守門**：`images_bytes` 非正整數即拒絕切換。
   **雜湊齊全證明不了收尾跑完**——每張圖都有合法 sha256 的候選版本，
   仍可能是 `fetch-images` 中途沒走完的產物。只修第 2 條的話，
   下一個早退長出來時沒有任何東西擋得住

**驗收**：C7c（驅動 `main()`，待處理 0 張仍重算且零 HTTP 請求）＋
C10d（`--publish` 對 `null`／`0`／字串／小數／負數五種都拒絕，且不消耗候選版本、
不留下半成品正式版；正整數才放行）。兩條各以變異實跑轉紅。

**留下的教訓**：這個 bug 逃過 137 個測試與兩輪 Codex 覆審，
因為它只在「排程真的跑起來、而且沒有圖片要抓」時才顯形——
**管線寫完不等於管線驗過**。同理，`verify-images.yml`（季度）至今仍是 0 次執行。

#### D28 資料更新時間頁尾

**問題**：頁面上唯一的時間資訊是 `meta.source_version`（TFDA 端的資料產生日）。
若 TFDA 三個月不更新，頁尾就停在同一個日期，**看起來像廢站**——
而實際上週更每週都在跑。「檢查過但來源沒變」與「根本沒在維護」在畫面上分不開。

**為什麼不塞進 `appearance.json`**：那份的 `meta` 刻意不含執行時間
（`fetch-appearance.mjs` §[9/9]），來源未變時位元組必須完全相同才不會產生假 diff。
「最後檢查時間」每次執行都會變，塞進去等於直接廢掉冪等。

**決策**：另立 `data/status.json`（`schema` / `last_checked` / `source_version` / `count`），
由 `tools/write-status.mjs` 在 **`--publish` 之後**寫出。頁尾兩個日期分開講：

> 資料版本：2026-08-10（TFDA 來源日期）· 最後檢查：2026-08-13 · 收錄：6,295 筆
> 每週一自動檢查 TFDA 來源更新

- **與 D16 相反，這條不 fail-closed**。狀態檔是裝飾性資訊，抓不到不得阻斷搜尋、不得進
  `#fatal`。降級鏈：`status.json` → 只顯示 `meta.source_version` → 整段 hidden。
  危險的方向不是「少顯示」，是**顯示一個過期或壞掉的檢查日期**——那會讓人相信資料是新的。
  因此 `daysSinceISODate()` 對壞輸入一律回 `null`，**絕不可回 0**（0 會被讀成「今天剛檢查過」）。
- **失敗的 run 絕不推進 `last_checked`**：write-status 排在守門／鏡像／verify／npm test／
  publish 全部通過之後。workflow 失敗時頁尾停在上次成功日，那是正確行為不是 bug。
- `last_checked` 距今 **> `STALE_DAYS`（14 天，＝錯過兩次週更）**時頁尾轉警示色並標出天數。
  這條讓「靜靜地壞掉」看得見。
- **時區**：排程是 UTC `17 20 * * 0`（＝台北週一 04:17）。直接用 `toISOString()` 會顯示成
  前一天。`taipeiDate()` 放 `search.js`，與 `IMG_ORIGIN` 同一條理由——
  **寫入端（管線）與判讀端（前端）必須用同一套日期定義**，各抄一份必然漂移。
- workflow 的提交步驟改為先 stage 資料與圖片判定 `DATA_CHANGED`，再寫 status.json，
  依此選兩種 commit message。代價是每週一個 ~200 bytes 的 commit，**那正是目的**。

### D19 只有搜尋列 sticky，條件面板隨頁捲動（v1.5，修正 P0）

### D21 不搬 object storage（v1.5 評估結論）

| GitHub 限制（2026-08-12 查證官方文件） | 本專案推估 | 佔比 |
|---|---|---|
| 發布站 ≤ **1 GB** | JSON 3.2 MB ＋ 圖片 100 MB ≈ 103 MB | **10%** |
| 來源 repo 建議 ≤ 1 GB | 同上，年度增量以新增藥品為主 | 遠低於 |
| 頻寬 **100 GB/月**（軟） | 每次冷啟約 1.2 MB（gzip JSON ＋ 24 張縮圖） | 約 8 萬次/月才觸及 |

**不搬的三個理由**（依序）：
1. **10% 的用量不構成問題**，搬遷是在解一個不存在的瓶頸
2. **會與 §9「無第三方 origin」的宣稱衝突** —— 與當初砍掉 Google Fonts 同一條理由
3. **會破壞 D12 的兩層發布模型**：現在 JSON 與圖片在同一個 commit 裡進出，
   `git revert` 就是完整回滾；圖片移到外部儲存後，
   「JSON 已發布、圖片還沒同步」變成一個 fail-closed 契約**看不到**的失敗態

**日後真要搬的最小接縫**：`app.js` 的 `imgUrl()` 是唯一組出圖片 URL 的地方，
把 `data/` 抽成一個常數即可切換。現階段**不預先抽**（YAGNI）。

### D22 圖片新鮮度驗證的 MVP 分級（v1.5 評估，**尚未改動行為**）

分級標準：**這一條在 v0.1 上線當天不做，會不會產生「使用者看不出來的錯」？**

**MVP 必要（留著，都在週更管線內、成本近乎零）**

| 機制 | 為什麼不能延後 |
|---|---|
| 零位元組視為失敗 | 來源對不存在的圖回 200 + 0 bytes。放行會寫出 0 byte 檔並宣告成功 |
| `isSha256()` 格式驗證 | 只驗「有值」的話，截斷／`"undefined"` 都算完成，那張圖**永久**避開一般排程 |
| 全有全無、失敗不回寫 manifest | 縮水後的數字會變成下一輪比較的新基線 |
| D12.1 provenance 三條 | 「新資料配舊圖片」是威脅模型第 3 項，這是唯一擋得住的地方 |
| D10.1 `?v=<sha8>` cache key | 換圖後 URL 不變，已快取的瀏覽器會一直顯示舊圖 |
| **抓圖時記錄 `src_bytes`** | 它是下載的**副產品**，當下不記，日後就只能靠全量重抓才補得回來 |

**可延後（v0.1 不排程也不會產生看不出來的錯）**

| 機制 | 延後的理由 |
|---|---|
| 季度 workflow 本身（`verify-images.yml`） | 第一次觸發在上線約 3 個月後，v0.1 期間根本不會跑到 |
| ② 隨機抽樣深驗 100 張（366 MB/季） | 它專防「長度剛好不變的改寫」。重新編碼一張照片幾乎不可能位元組長度不變；且對單張孤立改寫偵測力僅約 1.5%（規格已自承）。**建議留 ① HEAD 掃描、①有發現時才啟動 ②** |
| `probe_exceptions()` 恢復偵測 | `image-exceptions.json` 目前是空的，這條路徑現在是死碼。程式碼只有 20 行，留著不佔成本，但不必為它排程 |
| `--verify-all`（22 GB） | 已經不排程，維持人工稽核專用 |

**不建議延後的邊界**：以上延後的都是「鏡像的圖與官方現況是否仍相同」。
它們**不影響搜尋語意、不影響三值分區、不影響 fail-closed 發布**，
最壞後果是一顆藥顯示了舊照片 —— 而 §8.5 的安全文案已要求以原包裝人工確認。
若哪一條的失效會讓使用者**看不出來地**拿到錯的候選清單，那條就不在這個清單裡。

### D23 metadata-only 發布狀態（v1.6）

`npm run publish:metadata` 是獨立且明示的暫時發布路徑，不等同完整圖片就緒：

- 輸入仍必須是 canonical staging，且通過 schema、筆數、id 唯一性與圖片連結結構檢查
- 輸出保留完整搜尋欄位與官方 `src`，但強制把每個 `sha256` 清為 `null`，不引用尚未發布的鏡像
- `meta.images_complete=false`、`meta.images_bytes=null`（v1.11：原為 `0`，見 D38）
- staging 不被消耗，後續圖片首建仍可沿用原流程
- 原 `--publish` 仍拒絕任何缺少合法 sha256 的圖片；全量完成後標示 `images_complete=true`

因此就緒狀態由一個含糊的「有／無 manifest」拆成兩個可觀察狀態：搜尋資料就緒與圖片鏡像就緒。

### D24 低確定性結果使用證據抽屜（v1.7）

- 完全／字首／包含三級維持展開，不增加確定候選的操作成本
- 「部分符合」與「資料未提供」預設收合，摘要永遠顯示各自筆數
- 使用原生 `<details>/<summary>`，保留鍵盤操作與 disclosure 語意
- 卡片在首次展開時才建立；展開後仍沿用 D11 的每批 24 筆續繪
- 臨床安全提示維持固定顯示，不得移入任何收合容器

### D25 TFDA 官方仿單連結（v1.8）

- URL 由共用 `officialLeafletUrl(id)` 產生；`app.js` 不得自行硬編 origin 或路徑

- 連結位於詳細辨識資料下方，與每張圖片的「查看 TFDA 官方原圖」維持不同資訊層級

### D26 零條件入口狀態（v1.9）

### D27 外觀辨識卡（v1.9）

- 標註一／二同時缺值時，只顯示一次「刻字資料未提供」；僅單欄缺值時保留兩個來源欄名
